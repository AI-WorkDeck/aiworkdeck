# 前端：辨认、拆解、对应填入

这个 skill 的目的是**忠实还原**律师给的东西。给的可能是判决书、起诉状、答辩状、证据
目录，可能是扫描件或照片，也可能只是一段口述或一段提示词。前端做三件事：辨认、拆解、
对应到后端的图形模块一个一个填进去。

## 分工

**模型做读懂意思那一半。** 读材料（含读图，扫描件与照片直接看，不引 OCR 依赖；律师
大概率会传扫描件，不能因为难就砍掉这个能力）、认出材料含哪几个部分、抽事件、按容量把
字写到位。

**代码做可以算、可以验的那一半。** 算容量、验模型的输出、出图。代码**不做拆解** ——
曾写过一个按「日期间隔 + 文书名」切分的正则切割器，在真材料上切出三组同名、一组吞掉
六成句子，组名是「在“投标书”（投标文件第 8 页」这样的残句。哪几句属于同一件事，是读懂
内容之后的判断，正则拿不到。

贯穿全部的一条原则（沿用步骤四五六的设计）：**模型可以答错，但不许错得无声。**
凡是模型的判断，都要能对句子逐一核验，于是答错变成一次失败的检查，而不是一张错的图。

## 一轮交互

**读完材料直接给勾选清单，一轮定完，其余不问。**

    读材料（代码）→ 划分并给清单（模型）→ **用户勾选** → 抽取并出图（模型 + 代码）

### 为什么只有一轮

先前的设计是四问（问用途 → 问全部还是局部 → 勾选 → 问图名），其中「先问全部还是局部」
是**假省 token**：用户答完，模型照样要读全篇才能划分，一个字都没少读。作者指出了这一点。

真正省在哪，算过（材料一，46 句 1671 字）：

| 步骤 | 要读多少 | 能不能省 |
| --- | --- | --- |
| 划分（认出有哪几个部分） | 全篇 1671 字 | **省不掉**。判据是「这几句是同一件事」，不读完不可能知道 —— 这是成本的地板 |
| 抽取（为每个事项写文字） | 勾一个部分只读 179 到 504 字（全篇的 11% 到 30%） | **这才是省的地方** |

而抽取真正花的不是读，是**写**：每个事项要写文字、算容量、验子序列。勾三分之一的部分，
这些活就只做三分之一。所以勾选必须放在抽取之前、划分之后 —— 一轮，不是两轮。

### 那一轮问什么

清单上每个部分给四样东西，让律师不必信任模型的命名：

- **名字**（模型读懂之后起的，不是照抄文书名 —— 照抄会出现三组同名）
- **时间跨度与句数**，其中几句是已发生的事实
- **首末句原文**（照抄，不概括 —— 他看原文就能核对这一组是不是他要的）
- **这一段会画成什么图**，两种都可行时标出默认那一种

支持单选、多选、全选，也支持「你替我定」。**不答就全选。**

### 图种不单独问

图种是勾选结果决定的：勾「时效抗辩」那一段，材料自然是几个时点跨很多年（日期型）；
勾「工期与停工」，自然是几段期间（期间型）。所以标在清单里，勾的时候一并选了。

只有一种情形需要他真的选：**同一段材料两种图种都可行且都有意义**（日期齐全、跨度也长，
既能讲时效也能讲经过）。那时在那一行标一句「可画成日期型（讲时效）或编号型（讲经过），
默认日期型」。

### 其余一律不问

用途、图名、排布（横向纵向几层几列）、容量、字数、分页 —— 这些用户没有判断依据
（他不知道 40 字在横向撑不到 18 个事项），问了也答不上来。全部由代码算，
只在出图说明里告诉他结论与理由。

产物形状：

    [{"id": 1, "name": "股权转让协议的签订与价款约定",
      "sids": [0, 1, 2, ...], "span": "2014.03.12 至 2014.09.25",
      "n_facts": 7, "form": "编号型",
      "first": "<首句原文>", "last": "<末句原文>"}]

由 `check_model_output.check_parts` 验六件事：每句都落在某个部分里（一句不漏）、一句不
属于两个部分（否则勾两个部分会把同一件事画两遍）、部分数不超 8、名字不重复（同名的部分
无法勾选）、事实卡的首末句是原文而非概括、部分不许跨叙述块。

报错的顺序跟因果一致：**先报完整性，再报事实卡**。反过来的后果是漏了四句却报「事实卡
不是原文」（首末句按 min/max 算，漏句之后 max 变了），返工提示指向错误的地方。

## 容量：字数不是模型自己拿主意的

模块能装多少字是算出来的（`scripts/capacity.py`，它试排一次并二分实测上限）。顺序必须
是：先定取材范围与事项数 → 后端算出这一档的容量 → 模型按这个数写 `head`。

**容量既是上限也是目标。** 45 个事项纵向每个模块能装 63 字，只写四个字就是把图上的地方
浪费掉、把材料里的信息丢掉。`check_capacity` 因此有两档：超容量是错（必须在出图前拦住，
不许指望渲染器截断，图上不许出现省略号）；低于容量四成是告警（不拦，因为材料本身可能就短）。

## 正文默认不重复日期

**卡片顶端已经有日期那一行，正文里不要再写一遍。** 这是作者定的，来历是一张实图：
18 个事项、正文里又重复写了一遍日期时，卡片被压到 84px（卡内 60px），而
「2018年4月10日」这个原子有 90px 且按 D10 不许拆行，于是每张卡第一行的日期都冲出卡片、
被右边那张卡盖掉半个字。**同一批材料、同一个渲染器，正文不重复日期就完全正常**
（18 个事项全部完整，0 处溢出）。作者的判断是：每一行上面都已经写完日期了，
正文再写一遍没有太大意义。

**例外**：空间确实够、而且语境非要把日期再讲一遍（比如正文要强调「同日」「次日」这种
时间关系），那可以写。判据是空间与语境，不是习惯。

**长金额与长英文单词不必回避。** 它们和完整日期一样是不许拆的原子。这一档**按自然的
方式画就行，不要为了对齐去硬控**（作者定的）。实测按容量握手写字时（18 个事项、容量 30 字、
其中一条含「1,024,001元」），一行都不会伸出卡片 —— **前提是走握手**：容量由后端算、
前端按那个数写。绕过握手硬塞长句才会出问题，那不是几何的事。

## 交付：五种可编辑格式 + 一份溯源索引

出图那一步一次交付五种格式，做法是**复用 v1 的导出器，一个字都不重写**
（`scripts/export_formats.py`）：

| 格式 | 怎么来的 | 给谁用 |
| --- | --- | --- |
| SVG | 渲染器直出，主交付物 | 插进 Word、再编辑 |
| PNG | v1 的 `svg_to_png` | 预览、归档、微信发 |
| PPTX | v1 的 `export_pptx` **读最终 SVG** 逐元素转 | 讲课、庭前演示，每个对象可改 |
| VSDX | v1 的 `export_vsdx` 同上 | ProcessOn / Visio / WPS |
| drawio | v1 的 `export_drawio` 从语义地图建模 | draw.io 内继续改 |

pptx 与 vsdx 读的是**最终那张 SVG**，所以「交付的就是那张图」——同一套几何、同一种风格，
不存在两份实现漂开。这一条是 v1 已经解决好的，不要另起做法。

**唯一需要新写的是地图适配**：v1 的 drawio 导出器读 `ev["text"]` 与顶层 `date_text`，
而 v2 把正文放在 `head`、时间放在 `time` 里，另外多了 `numbered_multiband`、
`vertical_single_column`、`vertical_two_columns` 这几个 v1 没有的 layout 名
（几何上都是编号型时间轴，映过去即可）。**改的是喂给它的地图，不是它本身**（v1 冻结），
而且适配器不许改调用方的地图（有守卫）。

**每一种独立守护**：任何一种失败都只是少一种格式，绝不影响已经写好的 SVG。

## 扫描件与照片：三步读图

律师给的材料**几乎总有扫描件和照片**，尤其对方提交的那部分。不读图就永远只看得见
一方，而只看见一方的时间轴恰恰是最危险的产物。做法照 Anthropic 官方 `pdf-reading`
skill，三步，用的全是 poppler 自带命令，**不装模型、不调 API**：

    python scripts/read_image.py probe 材料.pdf        # ① 探测
    python scripts/read_image.py rasterize 材料.pdf pages/   # ② 150 DPI 栅格化
    # ③ 逐页看图，写转写稿

**探测的判据是「逐页可读字符数」，不是「pdffonts 有没有字体」。** 真材料上撞过反例：
一份 20 页扫描证据的 `pdffonts` 不是空表（第 20 页挂着一个空字体），而 `pdftotext`
逐页抽出的可读字符**全部为 0**。判据看错就会把扫描件当文字型，一个字都读不到。

**转写稿要存档，而且与喂管线的文本分两份。** 存档稿用 Markdown：每页一节、标页码、
开头写明「本文件是模型逐页读图所得的转写，不是原件」，律师据此翻原件逐页核对。
喂管线的那份是纯文本（`#`、`>` 这类标记会被切成句子）。

**转写稿一旦存档成材料，全套锚定判据原封不动生效**：正文必须是原句的子序列、
`raw` 必须逐字可查。实测 20 页纯扫描件跑出的 7 条正文全部通过子序列核验。

### 完备性对账在这条路上会变成自证，所以要外部锚

「句数 = 事件数 + 非事件数」是整套召回保证的地基，但转写稿的句子是**模型自己写的**，
少转一段，对账照样平。所以要拿材料**印在纸上的编号**当外部锚，转写时一并声明：

```jsonc
{"total_pages": 20,
 "series_totals": {"证据": 10, "维修明细序号": 38},   // 材料上印着的总数
 "pages_declared": [{"pages": "1", "series": "证据", "from": 1, "to": 6},
                    {"pages": "3-12", "series": "维修明细序号", "from": 1, "to": 38},
                    {"pages": "13-15"}]}              // 无编号的页只给 pages
```

`read_image.py check` 查两件事：**每一页都要有交代**（少一页就是无声地漏掉一段材料）、
**材料自带编号不许缺号**。总数必须单独声明、不许从声明的区间反推——试过取区间最大值
当上限，模型只转到第 30 项时缺号检查照样通过，那等于自己给自己划及格线。

### 表格里的一列日期，要逐条转写，不许压成一行

真材料上犯过：两份扫描合同的第 6 页是一张供货清单（序号 1 至 30，含一列供货时间），
我在转写稿里写成一句「供货时间出现：2020.2.20、2020.2.26、⋯⋯」。结果管线只认出
**3 个事实句**（两个签订时间 + 这一句），14 个供货日画不成 14 个事项 —— 一句只能
成为一个事项。逐条展开成 29 条之后才对。

**判据是：材料里每一行是一个独立的事实，转写稿里就该是一句。** 表格的一行、聊天记录
的一条、流水的一笔，都是一句。合并要留给骨架那一步（一个事项可以跨多句，同一天的
几条常要合并），**不要在转写时就合掉** —— 转写时合掉的，后面再也拆不出来。

这一条**有账目核对盯着**：压成一行时 `read_image.py check` 会报「共 30 项，转写稿缺
1 至 30」，因为逐条声明的编号区间对不上材料印着的总数。

**合并单元格照上一行填。** 那张清单的供货时间只在换日期时出现（序号 2、3 与序号 1
同一天），转写时要把上一个日期续下来，否则 29 条里只有 14 条有时间。

**总数按有内容的项数声明，不按最大序号。** 那张表印到序号 30，而第 30 行是空行，
所以 `series_totals` 写 29 —— 写 30 会每次都误报缺号（实测）。

### 页数多时把成本告知，但不替律师挑页

150 DPI 下约 1600 token 一页：20 页约 3.2 万，100 页约 16 万，300 页就超出多数模型的
上下文。页数偏多时 `probe` 会报出预估，**要不要全读、还是先给关键几页，由律师定**。
代码不替他挑页——挑漏了没人知道。

### 图像来源的事项要有名分

转写来的事项一律 `medium="image"`、`locator` 用「第 N 页」（不是转写稿的句号，
律师要能翻回原件），并在 `image_docs.json` 里列出读了图的材料。出图时会打印
「这些事项未经逐字核验」，`validate_map` 会核对数目。

## 分侧要不要起名：说得出就起，说不出就别分

有两侧时先问自己一句：**这个上下之分，说得出它是什么吗？**

- **说得出** → 写 `lane_labels.json`，图上出侧标签。**优先四五个字**（「供货方」「采购方」
  「支出」「收入」），够区分就行；名字长了会横向撞上第一根竖线，虽然会自动折成两行，
  但两行不如短名清爽。
- **说不出**（读了材料也定不下来，或者这个区分本来就不必解释）→ **骨架里不要写 `lane`**。
  这时图上是纯交替排布，不出侧标签。留着 `lane` 而不给名字没有意义：渲染器只在声明了
  `lanes` 时才按 `lane` 分侧，不声明时卡片是严格上下交替、完全不理 `lane`。

**只许写百分百确认的东西。** 侧标签能写的只有两类：材料上**写着的**身份或角色
（原告/被告、甲方/乙方、供货方/采购方、支出/收入、公司名），或者**有明确材料出处的
一方主张**。不许写法律定性 —— 自认、承认、否认、抗辩、违约、侵权、恶意、责任、属实、
存疑这类词是**判断**，不是材料上的字。不能确认就不写，要有谦抑性。

**同一个词能不能写，取决于它出自谁的材料。** 「被告主张」写在判决书里可以（法院居中
记载诉称与辩称）；写在原告的起诉状里就不行 —— 那是原告转述对方的话，而转述人自己是
当事人、有身份性。所以两侧必须出自**两方各自的材料**：判决书可以，起诉状对答辩状可以；
**只有一方的材料就是单侧**，不分侧、不出标签。

真实犯过：七份材料全部出自原告一方（起诉状、保全申请书、原告提交的付款计划与聊天截图），
图上却标着「原告主张 / 被告自认」——「自认」二字整份材料里一个字都没有。同一批材料里
5 条卡片正文全部通过子序列核验，因为正文有「只许删减不许改写」的铁律管着，
而侧标签当时没有任何来源约束。改成单侧之后，容量还从 42 字涨到 140 字（不必分层）。

**代码不会替你编名字。** 以前管线有一句兜底「原告主张 / 被告主张」，模型不给名字就用它 ——
真材料上出过事：支付宝流水两侧其实是支出与收入，图上却标着「原告主张 / 被告主张」，
而图看起来完全正常。那等于宣称一个材料里没有的区分。这句兜底已经删了。

**字数上限随事项数收缩**（`capacity` 会报出这一档的上限）：侧标签贴左边缘起排，
右边第一个障碍是首个圆点，事项越多卡越窄、余量越小 —— 6 项 8 字、10 项 5 字、18 项 2 字。
超了会在出图前拦住并告诉你上限，不会截断也不会缩字号。

## 两侧是什么关系：`lane.relation`

有两侧时，除了给泳道起名（`lane_labels.json`），还要说清**两侧是什么关系**
（`lane_relations.json`，形如 `{"P": "actor", "D": "actor"}`）。三个值取自泳道的定义
（语义分方：谁的主张 / 哪一层主体 / 哪个程序阶段）：

| 值 | 什么时候用 | 例子 |
| --- | --- | --- |
| `assertion` | 两侧各说一套、互相对读 —— **默认值** | 原告主张 / 被告主张 |
| `actor` | 两侧是不同主体或不同层级 | 母公司 / 子公司、总包 / 分包、支出 / 收入 |
| `stage` | 两侧是不同程序阶段 | 一审 / 二审、审理 / 执行 |

**为什么必须说清**：只有 `assertion` 时「同日相反主张」这条检查才成立。支付宝流水两侧
是「支出 / 收入」，同一天既有支出又有收入是完全正常的账目 —— 不声明 `actor` 的话，
75 笔流水会报出 6 处「同日相反主张」，而一处都不是。满屏误报会让真报警一起被忽略。

**不填等于 assertion**，所以已有的地图一个字都不用改；不确定就别填，宁可多收到一句
「请核对」，也不要把材料里真实存在的矛盾咽下去。

## 承诺与约定的时点不是事实

时间轴画的是**客观发生过的事**，不是**将要发生的事**。付款计划里的付款日、合同约定的
交货期限、承诺的整改期限，都是「将来要做」，不是「已经做了」。

这一类最险，因为它**过得了全部句法判据**：日期在材料里、精确到日、正文是原句的子序列，
`raw` 逐字可查——四条铁律一条都拦不住它。判据是句法的，不问语义，所以这一关只能在
判事实那一步靠读懂意思守住（见 `model-steps.md`「不算事实的几类」第五条）。

真实犯过一次的反面例子：一份被告盖章的付款计划列了四个付款日（5-18 十万、5-30 十万、
6-10 十五万、6-20 九万四千八百五十九点八六），四个日期四笔金额，**看起来是整套材料里
最好的时间轴素材**。但它们全是承诺。留下的只有「2022-05-12 出具付款计划并盖章」
这个已发生的事实。

**要画「到期未付」，得材料里另有记载**（付款回单、催告函、对账单）。没有记载就不画——
不许用「后来起诉了所以肯定没付」这类推断补上。这与侧标签那条是同一条谦抑性：
不能百分百确认的，不写。

## 忠实：只许删减，不许改写

抽丝剥茧要在容量之内做**删减**，不是改写。可检的形式是**子序列**：卡片文字必须是原句
的子序列，删词可以，换词、调顺序不行。由 `check_subsequence` 逐字核验，并要求每个事项
声明 `src_sid`（出自哪一句），否则无法核验。

**一个事项可以来自多句**，这是常态不是例外。真材料里现成的例子（材料一，句 29 与 30）：
「2015 年 2 月 3 日，被告向原告支付 320 万元。」加「此后被告未再付款。」合起来才是一个
事项。所以声明的是 `src_sids` 列表，按**升序**拼接后核验；倒序会被拒，因为调换句子顺序
不是删减而是重新组织材料。

第一版只允许一个 `src_sid`，这种合并必然误报，前端只能拆成两个事项或者绕过检查 ——
绕过就等于这条保证没了。

子序列加容量两条合起来，忠实与长度就都能被机器验证，不靠自觉。

**这条检查的限度要说清楚。** 子序列同时管住顺序，所以跨句「凑意思」多半会因为要调序而被
抓住（试过两个恶意例子：把「320 万元」挪到「未再付款」之后，凑成「没付这 320 万」的读法，
被拒）。但**顺序上恰好可行的凑法它挡不住** —— 那一层要靠事实卡与人工勾选兜：律师看得到
每个部分的首末句原文，也看得到自己勾了哪几段。机器保证的是「没有原文里不存在的字、
没有调序」，不是「意思没被改变」。

## 材料自身的矛盾：报告，不修正

真材料里出现过「2019 年 4 月交付全部设计成果」早于合同签订（2019 年 5 月）这种情形。
这不是抽取错误，是材料本身矛盾。规矩是**照材料画、另附一行说明**，不许悄悄改成合理的
日期 —— 改了就不是还原材料，而是替当事人整理事实。

## 非精确日期：按 anchor 落位

材料里「此后」「其间」「同年」这类句子很多，它们是已发生的事实，只是没有精确日期。
四档确定度里只有 `exact` 自带位置，其余三档要靠别的事项定位：

| 确定度 | 材料里的样子 | 怎么排 | 必须给 |
| --- | --- | --- | --- |
| exact | 2024 年 3 月 5 日 | 按 date | date |
| range | 2024 年 3 月至 6 月 | 按 from（它的不确定是长度，不是位置） | from、to |
| relative | 此后、其间、同年 | 紧跟 anchor 之后 | anchor |
| order | 只知道在某两件事之间 | 紧跟 anchor 之后；无 anchor 则按给定顺序 | 建议给 anchor |

**anchor 曾是个死字段。** 校验器一直要求 `certainty=relative` 必须给 anchor，而没有一个
渲染器读过它 —— 实测把 anchor 从「2」改成「4」，图上五个圆点的位置一模一样，位置实际由
列表顺序决定。这是最坏的一种情况：看起来像有规则，所以没人会去查；而模型按语义填的
anchor 与图上的先后不一致时，没有任何人会发现。现在由 `geom.order_by_time` 统一排序，
并有守卫盯着「anchor 改变指向、图上先后必须跟着变」。

**连带的一条：合成材料的日期必须单调递增。** 用 `2023/{i%12+1}` 这类循环日期时，第 13 个
绕回一月，按日期排序就打乱了交错、容量随之下降 —— 守卫会报「规范说横向，实际选了纵向」，
看着像规范错了，其实是测试数据假设「列表顺序就是时间顺序」。加上 anchor 排序之后这个假设
不再成立。

## 全流程与四份 JSON

**这一节由代码生成**（`python pipeline.py steps`），不手写 —— 手写的文档会与代码分家，
而「照着文档写却过不了检查」是最难查的一类问题：人会以为自己写错了。
守卫盯着三件事：模板说的检查器必须真的存在、步骤表列的命令必须真能派发、
步骤说要先写的文件必须有形状说明。

```
全流程（标着「用户」的那几步等他勾选，其余自动）：

  命令                    谁做    做什么                               要先写的文件
  --------------------------------------------------------------------------------------
  next                  代码    走到第几步、下一步跑什么、缺哪个文件（中途接手先跑它）
read <材料...>          代码    读材料、切句、认叙述块                       
  pick                  用户    第一轮：勾材料来源（含「全部」）                  
  span <编号|全部>          用户    第二轮：勾时间段（粒度按跨度自适应）                
  style <1-4>           用户    第三轮：呈报给谁 → 白描 / 奇川风 / 歸藏风 / 让 AI 定
  offer                 模型    划分并给勾选清单                          verdicts.json + parts.json
  budget <编号|all>       用户    勾哪几个部分                            
  capacity              代码    按真实骨架算形态与容量                       skeleton.json
  title '…'             模型    图名（容量内）                           
  render <出图.svg>       代码    校验 → 出图 → 顺带写溯源索引                 items.json

  另有 mark <编号|0>    用户  第五轮：深红标在哪一处（0 = 不标）
  ——它在抽取完事项之后、出图之前问，只有奇川风才问，所以不在上表的主序里。

四份 JSON 的形状与判据：python pipeline.py shape verdicts.json
（也可写 parts.json / skeleton.json / items.json）
```

标着「用户」的那几步都是勾选（勾材料来源 → 勾时间段 → 勾呈报给谁 → 勾哪几个部分
→ 勾标红哪一项），其余自动。**不写死轮数** —— 该问的才问，只有一份材料、日期不足八个、
只有一段内容、非奇川风，这几种情形各自跳过一轮。
每一份 JSON 的形状与判据用 `python pipeline.py shape <文件名>` 现查，不靠记性。

**勾选真的会限制抽取范围**：句子必须出自勾中的材料、日期落在勾中的时间段里；范围外的
事项在 capacity 那一步被剔掉并报出来，不默默画进去。没有日期的句子跟着它所在的材料走，
否则「此后」这类事项会被时间筛掉。

（这一条是补出来的：前两轮的勾选原来只写不读，与 anchor 那个死字段同一种毛病 ——
声明了、记录了、没人用。）

**时间那一档的判据只有一个出处。** 列清单与过筛都走 `pick.bucket_label`（日期 → 档）
与 `pick.in_bucket`（日期是否属于某一档，判据是「照同一个函数算出来的标签是不是它」）。
起因是接上之后仍漏的一处：过筛原来拿「标签里含不含这个年份」当判据，而季度标签里本来
就写着年份 —— 勾了「2024 年第 1 季度」，2024 年第 3 季度的句子照样进来。**跨度不到两年
才按季度列，所以季度正是第二轮唯一真正需要过筛的那一档，而它没生效。**
守卫漏过的原因也记下：原来的样本全是年档标签，被测的那一项在样本里不变化，
于是「拿年份做子串比对」这种写法也能通过。现在守卫两个方向都盯：季度档必须筛掉同年
别的季度（勾 Q1 时 Q3 必须出局），且 `bucket_label` 分到哪一档、`in_bucket` 就必须只认
那一档（把它写成恒为真会被抓住，验过）。

## 只有一个选项时不问

**问一个只有一个答案的问题是浪费用户的时间。** 两处已实现：

- **只投喂一份材料**（或只讲了一段话）→ 跳过「选哪一份材料」，直接进下一环节，
  并打印一行说明（材料名、句数、日期范围），让用户知道跳过了什么。
- **材料只覆盖一小段时间线** → 跳过「选哪个时间段」。判据是 `round_two` 只分出
  一档（或零档）：跨 0.8 年按季度分会得到四档，所以那种材料仍要问；
  只覆盖一个月的材料只分出一档，跳过。

守卫**两个方向都盯**：一份材料不许列出多行、跨 0.8 年的材料不许被误跳过、
只覆盖一个月的材料不许还去问。只盯一个方向的话，把跳过条件写成「永远跳过」也会通过。
