# 项目级版本记录（本地 Git）设计

日期：2026-07-28
状态：待实施
范围：v1 本地版本管理（含分支）。云端仓库与多人协作是 v2，本文只保证不堵路。

## 一、要解决的问题

律师在一个项目里反复修改文档，现在没有任何版本概念：改坏了退不回去，发给客户的是哪一版说不清，不知道某份协议这周被改了几次、改了什么。

目标是让律师能回答三个问题：

1. 这个项目从头到现在经历了什么？（时间线）
2. 这一版和上一版差在哪？（对比，且要看得懂）
3. 我能不能退回去？（回退）

并且全程不出现一个 Git 术语。

## 二、关键约束（来自现有代码）

这些是设计的前提，都已在代码中核实：

1. **磁盘布局就是用户看到的树**。`data/projects/{projectId}/{文件夹}/{文件名}` 原样落中文名（`buildPhysicalPath`，`ProjectFileService.java:117`）。所以在项目目录上建 Git 仓库，历史里的路径律师读得懂。
2. **数据库才是文件树的真源，磁盘只是投影**。软删除（回收站）不动磁盘文件（`softDeleteRecursive`，`ProjectFileService.java:330`）；物理重命名失败时代码回滚 `filePath` 但继续改数据库名（`ProjectFileService.java:298`）。因此**只跟踪磁盘文件不足以还原一个版本**。
3. **自动保存极其频繁**：2 秒 / 15 秒防抖（`LibreOfficeEditor.vue:370`）。按保存提交会瞬间刷屏。
4. **文档是二进制 docx**，平均 1MB（现有 258M / 256 个文件）。Git 每次改动存全量 blob，磁盘增长必须治理。
5. **已有一个文本级对比**：`GET /api/files/compare` 抽纯文本给前端红绿比对（`FileController.java:443`），配 `DocDiffViewer.vue`。可复用为降级路径。
6. **已有 `DocumentCheckpointService`**：AI 单轮内的内存态撤销保险，下一轮即清。与本功能不是一回事，各自保留。
7. **嵌入式编辑器仅桌面端可用**（`libreOfficePreferred`）。web/h5 下没有 LOWA，依赖编辑器的能力必须有降级路径。
8. **LOWA = 完整 LibreOffice 24.2.8**，UNO 接口可用，`.uno:` 调度已有成熟通道（EDITOR_ACTIONS 白名单）。

## 三、术语表（唯一的对外语言）

界面、提示、错误信息一律使用右列，代码内部可用左列。

| Git | 界面用语 | 说明 |
|---|---|---|
| repository | 版本记录 | 「本项目已开启版本记录」 |
| commit（自动） | 自动存档 | 「14:32 自动存档」 |
| commit（手动） | 存一版 | 按钮文案 |
| tag / milestone | 重要版本 | 需命名，如「发客户第一稿」 |
| branch | 另起一稿 | |
| checkout branch | 切到某一稿 | |
| merge | 采纳这一稿 | |
| conflict | 两边都改了 | 「这份文件两边都改过，请选一份」 |
| revert | 退回 | 「退回到这一版」 |

## 四、架构

五层，自下而上。

### 4.1 仓库层 `ProjectRepoService`（JGit）

选 JGit（`org.eclipse.jgit`）：纯 Java，无需外部 git 命令行，桌面端打包零额外负担。

**仓库位置**：git 目录与工作区分离。

- gitDir = `data/repos/project-{projectId}.git`
- workTree = `data/projects/{projectId}`

理由：避免 `.git` 出现在 `data/projects/` 下被 RAG 扫描（`ProjectRagService.java:94`）、压缩包导出、搜索等既有逻辑误伤。JGit 用 `FileRepositoryBuilder().setGitDir(...).setWorkTree(...)` 原生支持。

**忽略规则**（写入仓库的 `info/exclude`，不放 `.gitignore` 以免污染用户可见目录）：

- 单文件超过阈值（默认 50MB，可配）不纳入版本记录
- `client_uploads/` 之外的临时目录、锁文件

超阈值文件在清单中标记 `tracked: false`，界面上该文件的历史处显示「文件过大，未纳入版本记录」。

**对外方法**：init、commitAll、log、diffNameStatus、readBlobAtCommit、branch 增删列、checkout、merge、tag。为 v2 预留 addRemote/push/fetch 的位置但不实现、不暴露。

### 4.2 语义层 `ProjectVersionService`

把 Git 概念映射成业务概念。

**三类版本**，靠提交消息尾注区分：

```
修改了《股权转让协议》等 3 份文件

X-AWD-Kind: auto | manual
X-AWD-Note: 发客户第一稿
```

- 自动存档：`Kind: auto`
- 手动存一版：`Kind: manual`
- 重要版本：`manual` + 附注标签 `refs/tags/awd/milestone/{id}`

**署名**：git author 直接用当前用户名与邮箱；AI 落的版本 author 固定为 `AI Workdeck <ai@aiworkdeck.local>`。时间线上「哪些改动是 AI 做的」因此免费得到。

**提交消息自动生成**：从 `diffNameStatus` 拿到变更文件列表，映射回数据库里的中文名，生成「修改了《XX》等 N 份文件」。这句话就是律师在时间线上看到的内容。

### 4.3 文件树清单 `.awd/tree.json`

**这是本设计的核心机制**，解决约束 2。

每次提交前，把数据库中该项目的完整文件树序列化到工作区的 `.awd/tree.json`，随文件一起提交。节点字段：

```
id, parentId, name, isFolder, fileType, sortOrder,
filePath, isDeleted, tags[], tracked
```

于是「退回到某一版」= 还原文件内容 + 把数据库文件树同步到该版清单描述的状态。

**同步算法是差异同步，不是删表重建**：

- 清单有、数据库无 → 重建记录，优先沿用原 id；id 已被占用则新建
- 数据库有、清单无 → 标记为已删除（进回收站，不物理删）
- 两边都有但属性不同 → 更新属性

id 被占用而新建时，本次同步维护一张 旧id→新id 的临时映射表，**仅用于修正同一次同步内其他节点的 `parentId` 引用**，用完即弃。指向该文件的外部引用（标签关联、文件内链、变量绑定）按尽力而为处理：能改则改，改不动的保持原样并记日志——这些引用本来就可能因用户手动删除而失效，版本回退不引入新的一类错误。

这样回退不会丢失当前状态里的任何东西，且回退本身可再回退。

`.awd/` 目录对用户不可见（文件树读数据库，不读磁盘）。

### 4.4 提交调度 `VersionAutoCommitScheduler`

**触发信号**：文件保存成功、文件树变更（增删改移）、AI 轮次结束。

**防抖**：按项目维度设 2 分钟静默期。收到信号重置计时器，到点落一笔自动存档。

**强制落点**（绕过静默期立即提交）：

- 关闭文件（`flushSave` 之后）
- AI 轮次结束
- 手动存一版之前
- 切换稿件之前
- 执行退回之前

最后一条保证「退回」这个动作本身永远是可撤销的。

**保留策略 `VersionRetentionJob`**：每日一次，把 30 天前、且未被任何重要版本／手动存档／分支引用的连续自动存档区间压成一笔，保留区间末尾状态。

这是历史重写。为此：

- 执行前先打 `refs/awd/backup/{timestamp}` 兜底引用，保留 7 天
- 之后跑 `git gc`

**明确记为技术债**：v2 引入云端远端后，对已推送的历史做重写会破坏协作。届时必须重新评估——要么只在服务端统一执行，要么放宽保留期改为不重写。这条必须在做 v2 时重新决策，不能默认沿用。

### 4.5 差异呈现

三条路径，按能力降级。

**a) 文件级** —— `diffNameStatus` 给出「新增/修改/删除了哪些文件」。永远可用，是时间线节点详情的默认内容。

**c) 修订稿对比（主路径）** —— 生成一份带 Word 修订标记的对比稿，律师用日常看修订的方式读差异。

机制：

1. 后端 `GET /api/projects/{pid}/versions/{ref}/files/{fileId}/bytes` 从 git blob 取指定版本字节
2. 前端开一个 `tabType: 'version-diff'` 标签，内挂一个 LOWA 实例
3. 该实例 `load_document` 载入**新版本**字节
4. 把**旧版本**字节写入 MEMFS
5. 派发 `.uno:CompareDocuments`，参数 `PropertyValue{Name:"URL", Value: MEMFS 路径}`
6. 文档内产生修订标记，只读展示

需新增 office_thread action `compare_document {baseBytes}`，并加入 EDITOR_ACTIONS 白名单。遵守既有 zetajs 编组硬规则：sequence 传纯 Array，字节走 `Array.from(new Int8Array(...))`。

`.uno:CompareDocuments` 接受 `URL` 参数、可无对话框执行，已经过文档核实。但**在 WASM 构建下是否可用未经实测**，见第七节风险。

对比方向（哪一版作为当前文档）需实测确认，若与预期相反则对调步骤 3、4。

**b) 纯文本对比（降级路径）** —— 非 Writer 文档、或 web/h5 无嵌入编辑器时，走现有的文本抽取 + 红绿比对。复用 `DocDiffViewer.vue`，只把数据源从 fileId 换成 (版本, fileId)。

### 4.6 前端

左侧 rail 新增入口「版本」，左栏面板与资源管理器同级（版本历史是项目级导航，和文件树同一层）。

`VersionPanel.vue`：

- 顶部：当前所在稿（主线 / 某个另起的稿）+「存一版」按钮
- 主体：竖向版本图。节点 = 一版；重要版本加粗并显示命名；同一天的自动存档折叠成一行「这天还有 12 次自动存档」，可展开；分叉与合并用连线画出
- 点节点 → 详情：谁、什么时候、改了哪些文件。每个文件后面一个「对比」按钮，开对比标签
- 节点右键：退回到这一版 / 标为重要版本 / 从这一版另起一稿

FileTree 右键新增「这份文件的历史」，面板筛选到该文件。

新组件：`VersionPanel.vue`、`VersionGraph.vue`、`VersionDiffTab.vue`、`BranchSwitcher.vue`、`ConflictResolveDialog.vue`。样式沿用 awd-\* 类名约定（注意：该约定没有集中定义，各组件 scoped 内各自定义）。

rail 入口注册在 `frontend/src/config/leftSidebarPlugins.js`，面板分支加在 `project-overview.vue` 的 `sidebar-content`。

### 4.7 退回的实现方式

**退回不是历史重写**。「退回到这一版」= 新建一个版本，其文件内容与清单等于目标版本。时间线只会往前长。

理由：无数据丢失风险；退回本身可以再退回；律师的心智模型（时间线单向前进）与实现一致。

### 4.8 分支与冲突

「另起一稿」= 建分支并切过去。「采纳这一稿」= 合并回主线。

合并冲突逐文件列出，三选一：

- 用主线的这份
- 用这一稿的这份
- 两份都留 —— 把对方版本另存为 `{原名}（来自：{稿件名}）.docx`，并在数据库建对应记录

选择前可点「对比」看两份差在哪（走 4.5c）。

**不做段落级自动合并**。对 docx 既不可靠，也没法向律师解释。

`.awd/tree.json` 的冲突不暴露给用户，按「合并两边节点集合、同 id 冲突取目标稿」自动解决。

### 4.9 权限

CLIENT 角色看不到版本面板，相关接口返回 403。版本历史里有律师的内部草稿和试验稿，不应对客户可见。复用现有 `isAuthorizedForProject`。

## 五、开启方式

按项目选择开启，不给存量项目自动建仓库（258M 存量一次性全建会翻倍占盘，且不是每个项目都需要）。

第一次打开版本面板时询问「要为本项目开启版本记录吗？」，确认后做一次「初始版本」提交。未开启时面板显示引导。

## 六、错误处理

版本记录是保险，不是主流程。任何失败都不得阻断用户的正常操作——与 `DocumentCheckpointService` 同一原则。

- 仓库不存在 → 面板显示「未开启版本记录」+ 开启按钮
- 提交失败 → 记日志，面板顶部黄条提示，不弹窗、不阻断编辑
- 合并失败 → 回到合并前状态，提示「这次采纳没有完成，你的两份稿件都还在」
- 磁盘与数据库漂移 → 清单以数据库为准生成；磁盘上存在但数据库无记录的文件（如遗留 `client_uploads` 内容）照常纳入 git，清单中标记为「未登记」
- 超阈值文件 → 不纳入，界面明示

## 七、风险

**风险 1（最高）：`.uno:CompareDocuments` 在 LOWA/WASM 下未经实测。**

文档确认该命令接受 `URL` 参数、可无对话框执行，但 WASM 构建可能未编译该功能，且 MEMFS 路径能否被接受未知。

缓解：**实施的第一个任务就是最小验证**——在 lowa-e2e 中跑一次真实 compare，确认能产出修订标记。验证不通过则立即退回方案 b，并重新评估 c 的替代实现。这条不能排到后面，整个 4.5c 的设计悬在它上面。

**风险 2：保留策略与 v2 远端不兼容。** 见 4.4，已记为技术债。

**风险 3：磁盘增长。** 每次改动存全量 blob。缓解靠 4.4 保留策略 + 50MB 阈值。上线后需观察真实增长率再调参数。

**风险 4：对比标签占用保活池槽位。** `LIBRE_KEEPALIVE_MAX = 3`，一个对比标签吃掉一个。需在 LRU 逻辑中把对比实例标记为可优先淘汰。

## 七点五、实施分期

本设计范围较大（后端仓库层 + 清单 + 调度 + 保留策略 + 三条对比路径 + 五个前端组件 + 分支与冲突）。分四期实施，每期结束都是一个可用状态，不留半成品。

**第 0 期：验证风险 1。** 在 lowa-e2e 里跑通 `.uno:CompareDocuments`，确认 WASM 下能产出修订标记、确认对比方向。**不通过则整个 4.5c 重新设计**，后续各期的前端部分要相应调整。这一期不写业务代码。

**第 1 期：线性版本记录可用。** 仓库层 + 清单 + 提交调度 + 开启流程 + 时间线面板 + 文件级对比（4.5a）+ 退回。到此律师已经能用：存版本、看时间线、退回去。无分支、无修订对比。

**第 2 期：看得懂差异。** 接上 4.5c 修订稿对比与 4.5b 降级路径。到此第二个核心问题（差在哪）得到解答。

**第 3 期：分支。** 另起一稿 / 切换 / 采纳 / 冲突三选一。

**第 4 期：保留策略。** squash + backup ref + gc。放最后是因为它是唯一会重写历史的部分，前面三期跑出真实数据量之后再定参数更稳妥。

## 九、v2 预留

云端仓库形态已确认：**每人一个本地完整仓库，配一个云端 origin，推上去，别人从云端拉取**。即标准的分布式模型，不是「服务端单仓库 + 客户端视图」。

因此：

- `ProjectRepoService` 接口按「本地是完整仓库、远端是可选项」设计，预留 addRemote / push / fetch，v1 不实现不暴露
- 术语表预留 push → 「上传到云端」、pull → 「从云端更新」，v1 不出现
- 保留策略的历史重写必须在 v2 重新决策（4.4）

## 十、不在本次范围

- 云端仓库、推送拉取、多人协作
- 对话历史、变量库、尽调数据的版本化（各有各的生命周期，塞进来会让「版本」的含义变模糊）
- 段落级自动合并
- 非 Writer 文档的修订式对比（Calc/PPT 走文件级或文本级）
