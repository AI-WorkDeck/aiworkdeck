# 项目级版本记录（本地 Git）设计

日期：2026-07-28
状态：待实施
范围：v1 本地版本管理。云端仓库与多人协作是 v2，本文只保证不堵路。

## 一、要解决的问题

律师在一个项目里反复修改文档，现在没有任何版本概念：改坏了退不回去，发给客户的是哪一版说不清，不知道某份协议这周被改了几次、改了什么。

目标是让律师能回答三个问题：

1. 这个项目从头到现在经历了什么？（时间线）
2. 这一版和上一版差在哪？（对比，且要看得懂）
3. 我能不能退回去？（回退）

并且全程不出现一个 Git 术语。

## 二、核心模型：一次工作 = 一个版本

**这是本设计的组织原则，先讲清楚它，后面的技术选择都由它推出。**

律师的自然工作单位是「一段工作」——今天下午改了这份合同、上周花两天写完了法律意见书。不是「一次保存」，也不是「一个提交」。

所以：

- **第一次动了任何东西，一次工作自动开始。** 不需要点任何按钮。
- 这段工作期间的所有自动存档都归属于它，是它的内部细节。
- **结束工作时，整段工作作为一个整体进入主线时间线。** 结束时给它起个名字（不起就自动生成）。

主线上因此只有一串「完整的工作成果」，没有编辑到一半的中间态。「发给客户的是哪一版」这个问题于是有了干净的答案。

技术上，一次工作就是一个分支，结束就是合并回主线。但**分支这个词不出现在界面上**，律师看到的只有「本次工作」。

「另起一稿」用的是同一套机制，只差一个意图：

| | 结束时 |
|---|---|
| 本次工作 | 自动并回主线 |
| 另起一稿 | 不自动并，由你决定采纳还是放弃 |

这个统一让分支机制只需实现一次，而律师只需理解「工作」和「稿」两个日常词。

## 三、关键约束（来自现有代码）

这些是设计的前提，都已在代码中核实：

1. **磁盘布局就是用户看到的树**。`data/projects/{projectId}/{文件夹}/{文件名}` 原样落中文名（`buildPhysicalPath`，`ProjectFileService.java:117`）。所以在项目目录上建 Git 仓库，历史里的路径律师读得懂。
2. **数据库才是文件树的真源，磁盘只是投影**。软删除（回收站）不动磁盘文件（`softDeleteRecursive`，`ProjectFileService.java:330`）；物理重命名失败时代码回滚 `filePath` 但继续改数据库名（`ProjectFileService.java:298`）。因此**只跟踪磁盘文件不足以还原一个版本**。
3. **自动保存极其频繁**：2 秒 / 15 秒防抖（`LibreOfficeEditor.vue:370`）。按保存提交会瞬间刷屏。
4. **已有一个文本级对比**：`GET /api/files/compare` 抽纯文本给前端红绿比对（`FileController.java:443`），配 `DocDiffViewer.vue`。可复用为降级路径。
5. **已有 `DocumentCheckpointService`**：AI 单轮内的内存态撤销保险，下一轮即清。与本功能不是一回事，各自保留。
6. **嵌入式编辑器仅桌面端可用**（`libreOfficePreferred`）。web/h5 下没有 LOWA，依赖编辑器的能力必须有降级路径。
7. **LOWA = 完整 LibreOffice 24.2.8**，UNO 接口可用，`.uno:` 调度已有成熟通道（EDITOR_ACTIONS 白名单）。

**磁盘占用不是本设计的考虑因素**，按磁盘无限处理。不做任何配额、清理或体积治理。

## 五、架构

### 5.1 仓库层 `ProjectRepoService`（JGit）

选 JGit（`org.eclipse.jgit`）：纯 Java，无需外部 git 命令行，桌面端打包零额外负担。

**仓库位置**：git 目录与工作区分离。

- gitDir = `data/repos/project-{projectId}.git`
- workTree = `data/projects/{projectId}`

理由：避免 `.git` 出现在 `data/projects/` 下被 RAG 扫描（`ProjectRagService.java:94`）、压缩包导出、搜索等既有逻辑误伤。JGit 用 `FileRepositoryBuilder().setGitDir(...).setWorkTree(...)` 原生支持。

**对外方法**：init、commitAll、log、diffNameStatus、readBlobAtCommit、branch 增删列、checkout、merge、tag。为 v2 预留 addRemote/push/fetch 的位置但不实现、不暴露。

### 5.2 工作段生命周期 `WorkSessionService`

**这是第二节模型的实现，是本设计最核心的一块。**

**开始（隐式）**

收到第一个变更信号（文件保存成功 / 文件树变更 / AI 轮次结束）且当前不在工作段中 → 建分支 `work/{时间戳}` 并切过去。律师无感。

**段内（自动存档）**

- 触发信号：同上
- 防抖：按项目维度 2 分钟静默期，收到信号重置计时器，到点落一笔自动存档
- 强制落点（绕过静默期立即提交）：关闭文件（`flushSave` 之后）、AI 轮次结束、结束工作之前、退回之前

**结束（三个触发，同一个动作）**

1. 手动点「结束本次工作」
2. 关闭项目
3. 30 分钟无任何变更信号

结束动作：先落一笔自动存档收尾 → 弹窗让律师给这段工作命名（可跳过，默认「7 月 28 日下午的工作」）→ 合并回主线 → 切回主线。

单人场景下主线在工作期间不会变，合并总是快进，无冲突。

**未正常结束的恢复**

崩溃或强杀会留下未结束的工作段。下次打开该项目时检测到 → 询问「上次的工作还没结束，要合并进来吗？」，选项：合并 / 继续这次工作 / 丢弃。

**丢弃整段工作**

「今天下午改的全不要了」= 删分支 + 把工作区与数据库文件树同步回主线状态。这是本模型相对原设计的主要收益之一。

### 5.3 版本的三个层级

时间线上律师看到三层，从粗到细：

1. **工作段** —— 主线上的合并节点，带名字。默认只显示这一层。
2. **自动存档** —— 工作段内部，展开才见。
3. **重要版本** —— 附注标签 `refs/tags/awd/milestone/{id}`，加粗标记在对应工作段上。

提交消息尾注区分类型：

```
修改了《股权转让协议》等 3 份文件

X-AWD-Kind: auto | session | draft
X-AWD-Note: 发客户第一稿
```

**署名**：git author 直接用当前用户名与邮箱；AI 落的版本 author 固定为 `AI Workdeck <ai@aiworkdeck.local>`。时间线上「哪些改动是 AI 做的」因此免费得到。

**提交消息自动生成**：从 `diffNameStatus` 拿变更文件列表，映射回数据库里的中文名，生成「修改了《XX》等 N 份文件」。这句话就是律师在时间线上看到的内容。

### 5.4 文件树清单 `.awd/tree.json`

**解决约束 2。**

每次提交前，把数据库中该项目的完整文件树序列化到工作区的 `.awd/tree.json`，随文件一起提交。节点字段：

```
id, parentId, name, isFolder, fileType, sortOrder,
filePath, isDeleted, tags[]
```

于是「退回到某一版」= 还原文件内容 + 把数据库文件树同步到该版清单描述的状态。

**同步算法是差异同步，不是删表重建**：

- 清单有、数据库无 → 重建记录，优先沿用原 id；id 已被占用则新建
- 数据库有、清单无 → 标记为已删除（进回收站，不物理删）
- 两边都有但属性不同 → 更新属性

id 被占用而新建时，本次同步维护一张 旧id→新id 的临时映射表，**仅用于修正同一次同步内其他节点的 `parentId` 引用**，用完即弃。指向该文件的外部引用（标签关联、文件内链、变量绑定）按尽力而为处理：能改则改，改不动的保持原样并记日志——这些引用本来就可能因用户手动删除而失效，版本回退不引入新的一类错误。

这样回退不会丢失当前状态里的任何东西，且回退本身可再回退。

`.awd/` 目录对用户不可见（文件树读数据库，不读磁盘）。

### 5.5 不变量：历史永不重写

**已提交的版本永不删除、永不合并、永不改写。**

理由就是 Git 自己的理由：重写历史会让所有已经拿到旧历史的副本对不上，是分布式协作事故的唯一主要来源。v2 确认要推云端、别人要从云端拉取，一旦重写过的历史被推上去，协作就坏了。而且这种坏法有延迟——v1 单机跑得好好的，到 v2 才爆。所以这条**在 v1 就必须守住**，不是 v2 才要考虑的事。

因此不做任何形式的历史清理：不做 squash，不做 filter-branch，不做过期删除。

唯一例外是「丢弃整段工作」（5.2）删除未合并的分支——该分支从未进入主线，也从未被推送，删它不构成历史重写。

单测守这条：GC 之后所有可达历史完好。

### 5.6 退回的实现方式

**退回不是历史重写。**「退回到这一版」= 新建一个版本，其文件内容与清单等于目标版本。时间线只会往前长。

理由：无数据丢失风险；退回本身可以再退回；律师的心智模型（时间线单向前进）与实现一致。

### 5.7 差异呈现

三条路径，按能力降级。

**a) 文件级** —— `diffNameStatus` 给出「新增/修改/删除了哪些文件」。永远可用，是时间线节点详情的默认内容。

**c) 修订稿对比（主路径）** —— 生成一份带 Word 修订标记的对比稿，律师用日常看修订的方式读差异。

机制：

1. 后端 `GET /api/projects/{pid}/versions/{ref}/files/{fileId}/bytes` 从 git blob 取指定版本字节
2. 前端开一个 `tabType: 'version-diff'` 标签，内挂一个 LOWA 实例
3. 该实例 `load_document` 载入**新版本**字节
4. 把**旧版本**字节写入 MEMFS
5. 派发 `.uno:CompareDocuments`，参数 `PropertyValue{Name:"URL", Value: MEMFS 路径}`
6. 文档内产生修订标记，只读展示

需新增 office_thread action `compare_document {baseBytes}`，并加入 EDITOR_ACTIONS 白名单。遵守既有 zetajs 编组硬规则：sequence 传纯 Array，字节走 `Array.from(new Int8Array(...))`。

`.uno:CompareDocuments` 接受 `URL` 参数、可无对话框执行，已经过文档核实。但**在 WASM 构建下是否可用未经实测**，见第七节风险 1。

对比方向（哪一版作为当前文档）需实测确认，若与预期相反则对调步骤 3、4。

**b) 纯文本对比（降级路径）** —— 非 Writer 文档、或 web/h5 无嵌入编辑器时，走现有的文本抽取 + 红绿比对。复用 `DocDiffViewer.vue`，只把数据源从 fileId 换成 (版本, fileId)。

### 5.8 前端

左侧 rail 新增入口「版本」，左栏面板与资源管理器同级（版本历史是项目级导航，和文件树同一层）。

`VersionPanel.vue`：

- 顶部：**工作状态条** —— 「工作中（已改 3 份文件）」+「结束本次工作」按钮；不在工作段中时显示「主线」
- 主体：竖向时间线。默认每个工作段一个节点，带名字与日期；展开某段可见段内自动存档；重要版本加粗标记；「另起一稿」的分叉与采纳用连线画出
- 点节点 → 详情：谁、什么时候、改了哪些文件。每个文件后一个「对比」按钮，开对比标签
- 节点右键：退回到这一版 / 标为重要版本 / 从这一版另起一稿
- 工作段右键额外一项：丢弃这段工作（仅未结束的工作段）

FileTree 右键新增「这份文件的历史」，面板筛选到该文件。

新组件：`VersionPanel.vue`、`VersionTimeline.vue`、`VersionDiffTab.vue`、`WorkSessionBar.vue`、`ConflictResolveDialog.vue`。样式沿用 awd-\* 类名约定（注意：该约定没有集中定义，各组件 scoped 内各自定义）。

rail 入口注册在 `frontend/src/config/leftSidebarPlugins.js`，面板分支加在 `project-overview.vue` 的 `sidebar-content`。

### 5.9 另起一稿与冲突

「另起一稿」= 建分支并切过去，但**结束时不自动合并**。之后可以「采纳这一稿」（合并回主线）或「放弃这一稿」（删分支）。

由于主线在此期间可能已经前进（律师在主线上又做了别的工作），采纳时可能冲突。逐文件列出，三选一：

- 用主线的这份
- 用这一稿的这份
- 两份都留 —— 把对方版本另存为 `{原名}（来自：{稿件名}）.docx`，并在数据库建对应记录

选择前可点「对比」看两份差在哪（走 5.7c）。

**不做段落级自动合并**。对 docx 既不可靠，也没法向律师解释。

`.awd/tree.json` 的冲突不暴露给用户，按「合并两边节点集合、同 id 冲突取目标稿」自动解决。

### 5.10 权限

CLIENT 角色看不到版本面板，相关接口返回 403。版本历史里有律师的内部草稿和试验稿，不应对客户可见。复用现有 `isAuthorizedForProject`。

## 六、开启方式

按项目选择开启，不给存量项目自动建仓库。第一次打开版本面板时询问「要为本项目开启版本记录吗？」，确认后做一次「初始版本」提交。未开启时面板显示引导。

## 七、错误处理

版本记录是保险，不是主流程。任何失败都不得阻断用户的正常操作——与 `DocumentCheckpointService` 同一原则。

- 仓库不存在 → 面板显示「未开启版本记录」+ 开启按钮
- 提交失败 → 记日志，面板顶部黄条提示，不弹窗、不阻断编辑
- 结束工作时合并失败 → 保持在工作段中，提示「本次工作还没能收尾，你的改动都还在」，可重试
- 未正常结束的工作段 → 见 5.2 恢复流程
- 磁盘与数据库漂移 → 清单以数据库为准生成；磁盘上存在但数据库无记录的文件（如遗留 `client_uploads` 内容）照常纳入 git，清单中标记为「未登记」

## 八、风险

**风险 1（最高）：`.uno:CompareDocuments` 在 LOWA/WASM 下未经实测。**

文档确认该命令接受 `URL` 参数、可无对话框执行，但 WASM 构建可能未编译该功能，且 MEMFS 路径能否被接受未知。

缓解：**实施的第一个任务就是最小验证**——在 lowa-e2e 中跑一次真实 compare，确认能产出修订标记。验证不通过则立即退回方案 b，并重新评估 c 的替代实现。这条不能排到后面，整个 5.7c 的设计悬在它上面。

**风险 2：工作段边界可能不符合律师直觉。** 30 分钟空闲自动结束这个阈值是拍的。可能出现「中午吃饭回来发现上午的工作被自动收尾了」。缓解：阈值可配；自动结束的工作段允许「继续这次工作」（重新切回该分支并解除合并），而不是只能新开一段。上线后按真实反馈调。

**风险 3：对比标签占用保活池槽位。** `LIBRE_KEEPALIVE_MAX = 3`，一个对比标签吃掉一个。需在 LRU 逻辑中把对比实例标记为可优先淘汰。

## 九、实施分期

分四期（第 0 至第 3 期），每期结束都是一个可用状态，不留半成品。

**第 0 期：验证风险 1。** 在 lowa-e2e 里跑通 `.uno:CompareDocuments`，确认 WASM 下能产出修订标记、确认对比方向。**不通过则整个 5.7c 重新设计**。这一期不写业务代码。

**第 1 期：工作段与时间线可用。** 仓库层 + 清单 + 工作段生命周期 + 开启流程 + 时间线面板 + 文件级对比（5.7a）+ 退回。到此律师已经能用：干活、结束工作、看时间线、退回去、丢弃一段工作。无另起一稿、无修订对比。

**第 2 期：看得懂差异。** 接上 5.7c 修订稿对比与 5.7b 降级路径。

**第 3 期：另起一稿。** 分叉 / 切换 / 采纳 / 放弃 / 冲突三选一。

## 十一、v2 预留

云端仓库形态已确认：**每人一个本地完整仓库，配一个云端 origin，推上去，别人从云端拉取**。标准分布式模型，不是「服务端单仓库 + 客户端视图」。

因此：

- `ProjectRepoService` 接口按「本地是完整仓库、远端是可选项」设计，预留 addRemote / push / fetch，v1 不实现不暴露
- 术语表预留 push → 「上传到云端」、pull → 「从云端更新」，v1 不出现
- **历史不可重写（5.5）在 v1 就必须守住**，它是 v2 协作的前提
- 工作段模型天然适配协作：每人的工作段是分支，合并进共享主线，就是标准的 feature branch 流。v2 的主要新增是「结束工作时主线可能已被别人推进」，此时合并从快进变成真合并，走 5.9 已有的冲突处理

## 十二、不在本次范围

- 云端仓库、推送拉取、多人协作
- 磁盘配额与体积治理（按磁盘无限处理）
- 对话历史、变量库、尽调数据的版本化（各有各的生命周期，塞进来会让「版本」的含义变模糊）
- 段落级自动合并
- 非 Writer 文档的修订式对比（Calc/PPT 走文件级或文本级）
