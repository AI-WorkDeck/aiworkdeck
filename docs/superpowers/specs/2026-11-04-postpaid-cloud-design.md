# AI WorkDeck 按量后付费与云端生命周期方案

2026-11-04 · dev-board #1701 · 设计历史与审查依据。

用户已授权主任务定稿并实施至 PR 合并。下文保留设计阶段的建议及问题，经营口径以[实施政策](2026-11-04-postpaid-cloud-policy.md)为准；实施及验证记录另行记录，不以本设计稿证明功能通过。生产部署和实际删除不在本次授权范围。

## 一、目标和已确认边界

取消以订阅身份作为官方高级功能的准入条件。订阅继续发放原有赠送额度和权益；非订阅用户可使用官方云端功能与按量服务。赠送额度之外提供等额授信，允许后付费；超过授信三天未付提醒，五天未付清清理云端，不动本机。

用户随后明确确认：按本账户当期获赠额度面值1:1授信，不随剩余额度递减；超限停止新增付费操作；首次超限起算72小时提醒、120小时仍未付清则清理云端。以下同此一致的口径已经确定；具体赠额来源、单价、降额与清理执行细节仍需设计定稿。当前只交付方案与开发工作流，不启动真实扣款或删除任务。第三方广场商品、自带供应商 Key、独立买断权益不在取消订阅门槛的隐含范围内。

## 二、现状与改造范围

官网账户中心是唯一账务权威。`lib/credits.ts` 使用 credit_lots 区分充值与奖励，wallet_ledger 记流水；退款追溯原批次。`lib/subscription.ts` 管周期额度。Java 的 MobileBillingClient 读统一账户余额，无权自行建立另一份钱包。国内平台 AI、平台服务、跨设备传输已有扣费路径，但不能据此声称所有服务已接入统一后付费。

主仓 `CloudStorageQuotaService.persistentQuota` 对非订阅返回零，订阅最多3GiB；MobileBackupService、MobileVersionObjectService、MobileAssistantService、MobileCalendarService 等把空间资格当订阅资格。MobileRelayClientService 的后台同步与前端 MobileBackupConsent 也读 subscriptionActive。必须同时改变服务端准入和各端消费字段，不能伪造 subscriptionActive=true。

目前核查未发现持久云存储按占用时长扣费的独立实现。新计费必须覆盖普通云项目、备份和历史对象，且明确逻辑用量与物理成本的关系。现有安全配额、并发限制、账号归属、备份同意继续有效；取消订阅门槛不等于取消这些约束。

## 三、待定政策及建议

| 决策 | 建议口径 | 尚需明确的原因 |
|---|---|---|
| 等额授信基数（已确认） | 以当期正式授予的赠送额度面值1:1计算，不随赠额剩余值下降 | 仍需列明哪些赠额来源可计入；零赠额默认零授信，不擅自新增额度 |
| 授信续期 | 新周期替换上限，既有欠款占用新额度，不能逐月累加授信 | 防止续订不断放大欠款 |
| 超限后新增服务（已确认） | 暂停新增收费操作，保留登录、还款、账单、导出及删除 | 仍须承担存量存储和已授权在途成本；是否允许超限继续消费须明确 |
| 超限事件 | 已结算欠款超过授信形成事件；预占占满额度仅阻止新请求，不触发删库倒计时 | 预估不能成为删除真实数据的依据 |
| 时间（已确认） | 首次超限时间T，T+72小时提醒，T+120小时可执行清理 | 使用服务端UTC与具体日期，非自然日零点 |
| 还清 | 触发事件后付清已结算应付欠款才解除；部分支付不重置T | 按已确认“仍未还清”口径，建议全部已结算欠款付清；账务冲正应同步重算 |
| 存储价格 | 按GiB·小时累计，按日入账；面向用户显示月度估算 | 费率、币种、最低结算粒度须先定，不能虚构已存在价格 |
| 订阅存储权益 | 现有3GiB作为持续免费空间抵扣，超出部分计费 | 与“订阅权益继续保留”一致；免费空间不能再折算一笔赠额重复抵扣 |
| 清理对象 | 个人账户拥有的云端业务内容，不注销账号、不删除债务流水、不删他人数据 | 团队归属、共享项目、仅存于手机/云端的内容需逐类确认 |
| 提醒失败 | 记录失败并重试；建议无可核验告知时进入人工复核而非静默删数据 | 这会改变固定第5天删除的执行条件，需明确接受 |

授信单位使用账务最小整数单位；赠送 token 必须有明确的账务面值映射，不直接把不同模型的 token 数当作等额货币。国内/国际账户分别计价，沿用当前站点兑换规则，未授权跨币种共享授信。

## 四、资金与服务授权

保持充值、赠送、订阅权益、授信、欠款独立可追溯。消费资金顺序建议为适用的订阅赠额→适用奖励→充值余额→授信。保留现有用户选择的充值续用边界，迁移前明确如何获得后付费授权，不能借新规则反向改变旧请求的付款来源。

统一请求流程：报价及费率版本→以账户锁原子预占→执行业务→按实际用量结算→释放多余预占。每笔用量有服务端生成的稳定事件ID、账户及站点、来源任务ID、发生时间、资金来源快照、用量和费率版本。重复请求、供应商回调和定时重试命中同一唯一键，不重复收费。失败退款回原来源；已经到期的赠额不退成现金或复活到新周期。

剩余可授权额=可用赠额+可用充值+max(0,授信上限-已结算欠款-授信预占)。赠额、钱包预占也分别扣除，不能同一额度分配两次。长任务需给出最大预算，流式请求按可核验的增量续占；不能只在请求开始查余额。无法精确限制的供应商通道，必须说明风险上界与限额同步机制，不能把估算当硬额度。

授信占用不是可提现资金。还款到账优先清偿欠款，剩余才进入充值余额；重复支付通知只入账一次。退款、拒付、管理员调整与补录迟到用量均追加更正分录，不改历史流水。赠额到期或订阅结束不能消灭债务；费率变更不追溯改价。

最低数据模型：account_credit_policy（政策版本与额度）、usage_events（用量）、funding_reservations（预占）、debt_entries/repayments（债务及还款）、delinquency_cases（超限事件）、notification_outbox、cloud_cleanup_jobs/items。具体是否复用既有表在账务专项审查后确定，不为分层而创建重复权威。

## 五、云存储计量

以账户拥有的可计费对象为基础，对大小变化与持续时间积分。建议记录byte-seconds，按高精度整数累计，再转换到账务单位；小文件不逐文件向上取整。免费空间按同一时段抵扣。采用容量变化事件与每日全量核对，任务停机后按最后水位补算，幂等窗口防重计。

需覆盖：云项目文件、云备份、历史对象、回收站、未完成分块、待删对象、个人助理附件与其他真实占用。规则必须对每类列出计费状态，避免同一对象在文件表和备份表重复计费。临时中转继续沿用既有传输规则和有效期，不能无说明地同时收存储费。压缩/去重收益属于经营口径，不隐式改变用户账单。

清理冻结时刻停止新增上传与对象发布。建议自可执行清理时刻停止收存储费，系统清理故障不无限增加用户欠款；实际删除前的基础设施成本由平台承担，此为待确认的经营口径。预签名链接、进行中的上传及多段上传都必须被权限代次隔离。

## 六、欠费状态机与清理

正常→使用授信→超限宽限→已提醒→待清理→清理中→已清理。每个超限事件有独立ID、触发余额/授信快照、T与截止时间、通知记录、政策版本。用户看到具体金额和时间，不只显示“即将删除”。

清理前提供云端内容清单与导出，清楚标明仅在云端的文件。T时即时显示欠费状态和明确期限，T+72小时发送指定提醒；可增加不替代这两个节点的临近提醒。通知通过事务outbox可靠投递，多端去重，日志仅保留必要投递信息。通知渠道优先站内和已有可用渠道，是否发短信及其成本单独列入费率/运营配置。

清理开始前由账务权威核对仍未清偿、政策和时间有效，再签发与账户及事件绑定的清理授权。必须设计支付与清理的原子裁决点，不能“查一次余额然后慢慢删”。在删除批次之间重验，清偿后撤销未执行批次；已经完成的物理删除不能靠付款恢复，界面与账单必须如实说明。

执行先冻结云写入并提升syncGeneration，再生成对象级清单，标记不可访问，异步删除真实blob及派生数据；每对象记录结果，失败重试并复核，无结果不得标记完成。禁止按模糊目录前缀跨账户递归删除。存储供应商版本、回收站、索引、缓存与备份保留期分别列清，不能把移出UI称为物理清除。

“不动本机”是硬边界：欠费清理不生成普通文件删除同步事件，不调用桌面文件删除、项目删除、版本清理或系统回收站接口。仅撤销云副本及其引用；本地文件、项目、Git历史与对象库不动。清理后所有旧设备上传请求带旧代次必须被拒绝；建议还款不自动重传整个本地库，用户明确重新启用备份后才按新代次重新建云副本；此恢复交互待定稿。无桌面副本的云端或手机内容会永久丢失，必须在告知和导出界面中特别展示。

账号、登录凭据、必要支付与账务记录继续存在，用户仍能登录还款和查看清理回执。云内容删除不能被当成债务核销。团队/共享资源以所有者与付款责任归属判断，不能因个人欠费删他人文件；尚不支持正确分账的资源先列为上线阻断事项。

## 七、跨端契约

新增独立cloudAccess及billing状态契约，包含能力、阻断原因、余额分项、已用/可用授信、欠款、超限时间、提醒/清理期限、syncGeneration、服务端时间和政策版本。subscriptionActive继续如实反映订阅身份。能力至少区分新增收费操作、读/导出、还款、上传与同步，不用单一布尔值掩盖不同权限。

桌面、手机、小程序、Office/WPS按能力展示，不再要求先订阅才能启用云功能；充值与订阅是不同入口。收费前展示计量依据和可用额度，后台服务的持续费用在开通时说明。旧版本保留原字段语义，采用能力版本协商；无法正确处理清理代次的客户端禁止自动重传，明确提示升级，不通过伪造会员身份兼容。

所有新文案走项目多语种令牌，20语种校验、参数占位符和RTL布局同批验收。网络失败显示状态未知，不能当成免费账户、已还清或已清理。

## 八、迁移和上线次序

先加兼容数据结构及只读账务快照→影子计量与旧账比对→统一预占结算→客户端能力升级→有限测试账号启用后付费→提醒演练→合成数据清理演练→再决定生产启用。提醒和删除各有独立默认关闭的开关；不因服务代码合并自动开启删除。

存量用户不追溯计费、不把订阅到期日当作欠费起点。迁移记录现有充值、赠额、订阅和空间快照，确认政策后从明确生效时间计量；不能把未经通知的历史占用一次记为超限并当天清理。回滚可停新增授信、停清理，但已发生债务与还款账本不可回滚覆盖。对旧客户端的限制与提前通知作为同一发布条件。

## 十一、交叉审查后的补充裁决（2026-11-04）

两位原生代理分别复核账务与清理设计，未执行产品测试；以下已吸收为实施前必须明确的细则。

1. **授信内欠款**：现指示只有超限才计时。建议本期不增设月结到期日，授信内欠款持续占用授信、可随时还款；未来若增加账期，应作为新的政策变更，不在实现中暗加。
2. **被动超限**：订阅到期或政策调整导致授信降低，不回溯计时。建议从新上限生效且已结算债务超过上限时建立新的超限事件，提前显示额度到期影响；已有事件不因降额或续订重置。具体赠额来源表须列出开始/结束时刻，不能拿奖励24个月有效期随意推导“当期”。
3. **资金授权独立**：现有钱包续用开关只代表旧政策下的授权，不能自动作为后付费授权。新模式需展示统一资金顺序并取得明确接受，迁移前仍按旧授权执行。已接受新顺序的示例：赠额20、充值30、可用授信100，费用70时分别消耗20/30/20；未接受新政策且钱包续用关闭时，不自行跳过钱包生成债务。还款交易独立展示金额；已有钱包是否自动抵欠需在接受页明确，不能读取旧开关自行推定。
4. **删除不可逆点**：账户中心以同一账户事务裁决还款入账和批次授权。每批有唯一许可ID、事件版本、资源清单摘要、有效期；执行端在删除前原子领取执行许可，领取前到账取消，领取后这批可能继续执行，后续批次取消。许可过期不允许重领旧批次，超时状态需对账，不能直接认为未删除。用户界面以“清理已开始，部分内容可能无法恢复”说明，不能承诺付款瞬间阻止已授权删除。外部支付已扣款但回调未到时尚不能证明账已清，需支付查询与短期核实状态阻止误清；最长等待及故障复核策略在实施接口审查中定清。
5. **部分清理后恢复**：增加PARTIALLY_PURGED状态。付款后未领取许可的对象解除隐藏并恢复读/导出，已删除对象保留缺失回执；已领取的对象先完成结果核对，再决定可见性，不把“请求已取消”当作文件存在。恢复时再升代次，旧任务不能继续删或上传新对象。
6. **明确停计费时点**：建议统一以T+120小时停止存量存储用户计费，而非实际worker启动或提醒复核完成时刻；等待人工复核和系统清理失败成本由平台承担。超限至该时刻存量空间继续按公布费率累计，但新增收费操作已停止。导出流量建议在宽限期单独提供一次免计费完整导出，成本及限制需定稿。
7. **历史迁移**：已有shortfall是平台历史缺口，不转为用户债务。旧在途请求继续使用原资金授权与原周期，禁止自动挂到新授信；新协议生效后创建的请求才可用新额度。国内/国际、AI/Skill、同步和异步网关、传输均须逐路径列出适配证据。
8. **客户端扩面**：W4包含iOS、小程序、Android、Harmony、桌面及Office/WPS实际消费入口。手机契约按后端OpenAPI→pull-api→生成与check次序更新。iOS当前云文件下载报价固定为0；若该下载计费，必须同步改报价和确认，不得先显示免费后扣费。
9. **金额不混淆**：当前订阅售价与额度面值不是同一个数字，主任务核对saas-pricing.ts记录monthlyCents=74500、weeklyCents=20000；此处沿用其账务单位，不把售价149直接作为授信数额。最终前端展示应复用现有Credits换算且以账户返回的实际赠额为准，不在客户端硬编码示例值。

### 示例时间线（假设单价已确认，仅说明状态）

账户当期赠额面值100 Credits，对应授信上限100 Credits。赠额用完且充值用完后，可形成100 Credits授信内欠款。到达上限时新请求已因无法预占而停止；持续存储或已授权在途结算可能使欠款达到101，从该笔结算的超限时间T起计时。T+72小时仍未清偿发送提醒，T+120小时仍未付清进入清理裁决。用户在T+96小时还10，欠款降为91但该事件不因此重置；全部还清才撤销。这个算例说明“在授信额度内暂停授权”与“实际超过授信才启动倒计时”并不矛盾。
