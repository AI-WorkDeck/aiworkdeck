# 轻量交互与报告选择

首次说明：事实确认→是否需要DPIA→简洁内部风险与整改→按用户选择出报告。实质方法遵循workflow中的EDPB指南定位；此处只规定交互展示。

## 事实与追问
输出前必须完成[source-trace.md](source-trace.md)的来源索引与具体差额核对；先展示生命周期等已知事实及原文定位供更正，再问本阶段缺口，并说明问题对筛查/风险判断的具体影响。不得用一个大主题代表若干已知/未知子项，也不得只有问题而没有事实。
首轮提供简短生命周期概览和集中问题包；详细可追溯事实清单保留并给入口，不默认在对话粘贴全部工程表。每题写原问题、所需事实、影响及建议材料；答案按原问限定范围，保留未知和冲突。先补筛查必需事实，不将正式模板全栏作为首轮门槛。
用户已答“不知道”“尚未设计”要记录其准确对象，不反复追问直到获得理想答案。不要让用户判断控制者、法律基础等法律问题，转成可观察的决定行为。用户没有成文材料时可接受真实业务说明，记录来源。

允许为实质缺口停下来等待，但每项未决内容须按source-trace.md展示“影响的具体判断、暂停范围及理由、可继续事项、恢复条件”。不把问题数量少或不停顿当作成功标准，也不把仅缺欧盟代表、人名或审批安排当作实质分析的全局阻断。混合问题先拆子项：传输保障内容与内部负责人姓名的重要性不同。

## 简洁内部评估
筛查需要DPIA后，默认摘要约1—3页及风险/整改清单，非硬性页数上限；复杂问题按组展开，不能省略法律分析。
每风险必有：法律条款/指南定位及效力→事实如何构成风险→级别及理由→措施和建议/验收。完整论证保留底稿。
分清缺事实、已知缺陷、待验证措施。拟议不等于已实现，用户称已整改不等于效果已经验证。交付后供用户选“整改补充后出报告”或“现在出待完善草稿”，不默认生成正式Word。

## 留空与批注
- 已确认事实、已确认尚未设计、既有缺陷和有依据的整改写正文，不加重复答案式确认批注。
- 用户现在要报告时，未知答案栏留空，不填假设、泛化主体或推测期限；部分未知仅留空对应部分。未知选择不勾选，不能默认否。
- 原生批注锚定空回答段或字段标签：待补充/确认（具体问题和证据）→合规影响（影响的判断及限制）→建议（建议谁从哪里取得信息或处理）。
- 依赖未知事实的结论保持未定，不给伪确定等级或批准；草稿标明评估未完成。允许留空交付不等于降低完整评估标准。
- 答复进入新版本后，重评对应正文和结论，再解决批注，不只删除批注而留下旧假设。

## 每轮更新
先核对评估归属，再展示“新增/变化→哪些判断需重评→仍需补充→下一步”。不重写未变化部分，不继承过期确认或批准。无完整国家连接时不得宣称符合当地全部要求。筛查不需要则结束本轮并记录复评条件，不等同业务整体合规通过。
