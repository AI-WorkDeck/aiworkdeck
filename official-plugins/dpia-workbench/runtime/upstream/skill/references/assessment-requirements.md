# 评估反推事实：通用契约 v1

## 法律专家的工作顺序

先从候选国家的法律、指南和适用模板识别评估问题，再反推每项判断所需的事实。国家不明可先研究共通问题并补问连接事实；研究不等于法律适用已确定。不能等事实冻结后才读规则；应后置的是事实依赖的结论。

五层：共通事实封装 → 评估问题/事实需求 → 法域规则扩展 → 场景扩展 → 模板映射。共通层统一证据、版本、状态和关联方式，不统一各国结论、阈值或表格栏目。本版仅GDPR及其相关成员国适配；SA等既有资源只为历史复现。

## 共通问题骨架（不是固定事实必填表）

| 评估问题 | 反推事实示例 |
| --- | --- |
| 何种法律、范围及程序可能适用？ | 实际国家连接、实体、活动、阶段、规模、持续性、特殊人群；不从界面语言推定市场 |
| 谁为哪个目的决定处理？ | 分目的的实体身份、决定权、指示、自主用途；不从系统名称推断处理者 |
| 处理什么人的什么数据？ | 人群关系、原始/推断字段、可关联标识、来源与精度；敏感分类留在法域层 |
| 数据如何流转和退出？ | 分活动的收集、传输、使用、存储、访问、保留、备份、删除、权利退出及异常路径 |
| 法律基础要件是否成立？ | 服务关系、选择机制、必要联系、利益目的；按候选基础动态派生问题，不要求用户做法律判断 |
| 是否必要且相称？ | 字段/频率/期限与目的联系、时效、收益依据、侵入较少替代的效用与限制 |
| 个人能否理解和控制？ | 告知时点、默认选项、拒绝/撤回后行为、查询/更正/删除及账户变化 |
| 算法有什么实际后果？ | 输出用途、接收人、行动后果、人工介入时点/权限、纠错渠道 |
| 如何影响个人权益？ | 正常处理与异常事件的影响机制、受影响人群、可识别性、损害路径与发生条件 |
| 措施是否足以应对风险？ | 设计、责任、适用系统、实施状态及效果依据；设计评估与运行验证分别立需求 |
| 接收、传输及专项如何安排？ | 实际实体/地域/访问/再利用、指示合同、专项范围/状态；不预设外部供应商 |
| 谁参与、决定和复评？ | 适用意见征求/审批/监管程序的触发事实、变化监测、责任与记录；国家程序独立扩展 |

每活动按骨架检查遗漏，不机械要求相同数量记录；不适用须有依据。“已有security_control”不代表证据足够。治理事实关联实际活动，不虚构治理目的；研发等自主二次用途与主服务拆分。

## 可执行结构

`assessment_plan`由`schemas/assessment-plan.schema.json`约束。status=building/reviewed表示需求计划成熟度，不是法律审核通过；phase=design/pre_launch/operational与文档meta.stage独立。

问题包含ID、问题、core/jurisdiction/scenario层、适用阶段、活动范围、规则required_facts逐项映射、模板栏目定位、事实需求。规则效力、法源、版本仍存规则包/来源注册表；当地新增义务先扩展并核验规则包，不用模板替代法源。

需求包含描述、规范化predicate、值类型、活动ID、对本问题的blocking/advisory重要性、可接受实施状态/材料类型、事实ID、satisfied/missing/not_applicable、充分性或缺口理由、补问/验证建议。一个事实可被多个问题复用，重要性可以不同。活动范围须一致；系统、地域、时点、版本、正常/异常条件还须结合事实context与来源人工核对，不以ID匹配替代语义核验。

字段集合可为array事实：同一来源、活动、上下文、状态无需逐字段复制。混合主体、目的、地域、来源、状态，或需独立补问时拆分。对象/数组内部业务含义和精度由需求描述约束并人工审查；本版不是完整行业字段本体。
跨活动共通事实使用activity_id=null及明确的scope_activity_ids，避免虚构“项目治理”处理活动或复制事实；不得默认对所有目的都适用。单活动事实仍用activity_id。

satisfied只表示事实足以进入判断，不表示合法或控制有效。not_applicable须有来源的否定布尔事实和理由；复杂适用问题拆出适用条件及证据，不能仅填N/A。缺证据保持missing。

## 门禁与确认

以下全覆盖契约用于完整评估，不是首次筛查的门槛。筛查按workflow.md只建立对应事实与确认快照；筛查需要后再展开其他需求。用户提前出报告时未满足需求继续missing，缺失字段留空批注，不能批量填满足或伪造确认。

本契约的blocking只决定所绑定问题能否作出充分结论及完整门槛是否满足，不意味着其他活动/判断都停止。当前交互的暂停范围另按source-trace.md记录，并在`affected_judgments`引用已存在的评估问题/规则ID（尚未建档时写具体判断名称）。程序事项不得仅为继续分析而标成advisory或not_applicable：保留适用义务和完成限制，只缩小它对其他判断的阻断范围。

### 共用需求与项目程序：计划契约 1.1

主记录仍为schema_version=0.5.0；新增计划显式设置`assessment_plan.contract_version="1.1"`。未声明或为1.0的旧计划继续使用内联需求及逐活动覆盖，不能使用新字段绕过旧语义。

- `shared_requirements`定义共用需求：保留完整predicate、类型、证据接受标准、事实ID、状态、充分性理由和补充建议，用非空`scope_activity_ids`取代单活动ID。不存重要性；相同事实但充分性标准不同，不合并为同一需求。每项所引事实须支持整个定义范围，不将若干不相同活动的局部证据拼成共通断言。
- 问题保留`requirements`（可以为空），可另设`requirement_refs`，每次引用包含`requirement_id`、非空`activity_ids`、`importance`和`rationale`。引用范围必须同时属于定义与问题范围，不默认全项目；重要性属于本次判断，不可在引用处改写证据标准、状态或事实。未满足的blocking引用仍阻塞；未来验证和不依赖的advisory仍单列。
- `rule_scopes.coverage_level`默认activity。只有规则包显式标记`project_procedure=true`的程序规则可设置project，并说明项目程序的影响活动及范围依据。当前EU仅C09–C13开放此种结构：不改法源、适用条件或required_facts。绑定项目程序的问题必须显式包含全部影响活动，每个活动都须有足够的当前阶段blocking输入；不能只回答一个活动或缩减范围换取通过。活动特有的目的、合法性、风险等仍逐活动审查，项目程序也不替代它们。
- 共用定义、引用范围、重要性、程序范围变化均使基线摘要失效，重新确认受影响依赖；未引用的共用定义不能成为结论输入。渲染器分别展示一次定义、多处引用及项目程序影响范围。

这是引用结构标准化，不是语义充分性的自动判定。范围—规则—要件计数减少不表示法律义务减少，也不证明评估已完成。

先用rule_scopes为每条选中规则定义适用活动、事实依据和理由；程序要求规则都有范围记录，不将所有国家要件机械乘以所有活动。项目共通程序可关联其影响活动并复用共通事实；排除某活动须有理由及依据，不能静默裁剪。当前阶段blocking需求须满足，每个required_facts在该规则的活动范围内映射并获支持。activity_facts等共通词须展开成具体判断及充分性标准再标记reviewed；程序不鉴别随意映射是否语义充分。未来阶段问题保留不阻塞设计；advisory缺口展示但不得补足必要结论依赖。

返回事实清单、需求及缺口并取得真实human_confirmation记录之后，再计算`fact_requirements.baseline_digest(d)`写入meta.fact_baseline_digest并冻结版本。摘要不是签名或同意证明，只检测确认后材料、事实、范围、阶段、规则版本及需求变化。变化后确认受影响部分并记录新版本/摘要，不自动生成确认。

结论只能引用本阶段已审阅需求中足够的事实。非输入未知事实及未来验证可保留；若实际决定结论则提升为blocking。完整DPIA仍须通过法律覆盖、实体分析、风险及人工程序门槛。

## 能力及兼容边界

程序检查类型、引用、活动范围、阶段、证据状态、映射覆盖和基线变化；不判断材料真假、语义充分性、必要性或法律结论。template_refs仅保留人工核验后的栏目定位，不证明已读官方原件。新增国家/场景先定义问题和事实，再补映射及代表性正反例。

0.1–0.4保留读取和原有校验语义用于历史复现；新评估/复评必须迁移0.5。旧测试通过不代表通过新契约。
