# GDPR阶段性交付

实质依据为workflow中的EDPB指南；输出样式不改变评估方法。

## 默认输出
事实阶段：概览与集中问答，完整清单按需。
筛查阶段：需要/不需要/暂不能确定、对应法律和当地清单依据、范围和复评条件。
内部评估：固定为“评估事实—评估结果—集中整改清单”，不默认套正式模板，也不把机器底稿展开成业务报告。具体呈现契约见下节。
内部清单及复评文件必须由`internal-review`从当前assessment.json和已核对来源映射生成，不另写脱离risks/actions的结论。聊天可概括文件，但不得新增未记录的风险或改动等级。正文保留简洁来源脚注和风险/整改编号；完整来源、UUID、hash、状态码、依赖及校验信息移入同名.audit.json。命令只保证关联与呈现约束，不保证法律正确或事实提取充分，仍须核对原文语义和法律适用。
该命令不要求完整事实基线冻结；缺口仅限制对应判断。最终筛查尚未完成时，使用`--conditional-basis '具体条件、范围及不能定论的部分'`输出有限分析，不能用这个参数虚构确认或规避整体对象不明的暂停。有依据结束DPIA筛查的，应输出筛查结论，不强行生成风险。没有有依据的风险记录时回到事实/筛查，不填写占位风险。
交付状态写“已完成本轮事实梳理/条件分析/部分复评”，并列出未完成范围；不单独写“评估完成”。后续新增信息必须更新结构记录、来源映射和暂停范围后重新生成，不能只在新报告复制旧风险标题和通用整改。
正式报告：仅按用户选择整改后生成或现在生成；使用适用模板或GDPR必要内容结构。没有模板不等于无法评估；模板草案不等于现行强制格式。

## 内部报告的三部分

1. **评估所依据的事实。** 先说明范围、阶段、目的、人员及参与主体；按采集/产生、传输/跨境、使用/二次利用、存储、接收/分享、保留/删除、缓存/备份整理生命周期。单列告知、开通/选择/撤回/关闭、访问/携带、更正/复核/申诉、删除/限制/反对、解绑/换主/退出的实际安排，以及现有措施和设计/实施状态。用业务语言说明处理如何发生，不只列字段ID；“有导出功能”不能自动写成“已满足可携带权”。材料明确、用户确认、未说明、尚未设计分别保留；固定本轮依据不等于强制事实冻结。未有记录的展示主题只标“事实清单尚未明确”，不得自动说PRD没写或新增问题。
2. **评估结果。** 先筛查及结论范围，再列必要性/比例性、法律基础、权利、安全、跨境及程序等评估维度的当前分析/限制。已有具体风险不能冒充所有维度已完成；不能因risks存在就将content规则改成met。各风险保留法律定位、事实到个人损害的推理、可能性/严重性与等级理由，以及整改关联和效果限制。未知依赖只限制对应判断。
3. **整改清单。** 每个action只出现一行，通过risk_ids关联一个或多个风险；列措施、优先级、责任/时点、验收和状态。风险段仅引用整改编号及解释措施作用，不再重复整张整改表。未知责任/时点/优先级保持未确定；不能从高风险标签自动生成优先级或声称必须上线前完成所有治理待办。

`intake-review.json`新增`report_topics`，是经语义核对的主题→fact_ids映射，不是新的事实或法律结论。允许一条事实支持多个主题，必须覆盖全部已记录事实；程序不根据关键词猜权利实现。可用键：scope、purpose、people、collection、transfer、use、storage、sharing、retention、backup、notice、choice、access、correction、deletion、exit、safeguards。可省略尚无记录的主题，输出明确未确定；不能省略已提取事实。示例：`{"scope":["F1"],"choice":["F2"],"exit":["F2"]}`；具体ID取自当前底稿，按原文判断归属，不能套测试答案。事实段文本来自已核对的fact_links.summary；摘要必须保留事实关键细节及不确定性，不能借重排增加实现承诺。可选`action_priorities`以action_id→已论证的中文优先级说明记录，未提供不推断。

技术索引保存版本/输入摘要、正文摘要、来源与事实/风险/措施映射及未决记录，用于追溯，不作为业务方必读正文。任一目标文件已存在则拒绝覆盖；修改报告先更新底稿或呈现映射后使用新文件名生成。旧trace仅需补充呈现映射，不伪造新用户确认，也不改变原风险结论。模板正式报告的留空/原生批注规则不变。

凡已映射事实的权利主题，须另在`report_topic_limits`中用相同主题键说明事实覆盖范围及未明事项。例：“已知支持PDF报告导出；权利请求入口、数据覆盖及办理流程仍未明确。”不能仅把导出、总开关、后台人工处理归类到权利章节，就暗示完整权利实现；有完整证据时说明已知覆盖及其来源，不机械写成未知。该说明仍需由模型核对原文，不由脚本推断。

## 筛查答案与维度进度（0.7.5）

**筛查必须有答案。** 已通过screen的required正常显示“需要开展DPIA”。未能最终确认时，在intake-review中显式记录`screening_conclusion: {"result":"required", "rule_ids":["EU-T04"]}`，并用`--conditional-basis`写实际前提；程序显示“需要开展DPIA（条件性结论）”及所引规则已有analysis/事实/法源。不从一段限制文字猜结论，不自动用指标个数判必需。required至少引用一条有事实支持、已实质论证、未因变更失效的完整trigger；存在已主张例外的冲突须先解决。无法支持明确需要时用result=undetermined并指向已有具体未决分析；不能只保留一句“待评估”。not_required必须先走筛查结束及理由记录，不能在风险报告里用条件参数跳过否定结论的核验。原用户确认门槛不删除，不为得到required伪造确认。

**各维度按实际工作分别记录。** 在assessment.json对应content规则保留analysis作为唯一论证正文、fact_ids/source_refs作为依据，新增review：

```json
{"progress":"partial","finding":"issues_identified","limitations":"已分析持续保留设计；逐目的期限依据和退出处理尚待补充。","risk_ids":["R-03"],"action_ids":["A-03"]}
```

- progress：not_started（尚未开展，须解释具体原因）、partial（已开展，部分判断待补充）、complete（该维度分析完成）。不是整改进度。
- finding：issues_identified、no_issue_identified、undetermined、not_applicable。分析完成可以发现不合规或风险，不等于通过；“未发现问题”也须限定已评估范围。
- limitations：指出仍不能判断的具体子项及所缺材料；partial/not_started不可空。risk_ids/action_ids关联已有论证与整改，所有输出风险必须归入已开展分析的维度。整改是否进行/关闭继续读取actions.status；措施是否实施/验证继续读取controls，不能被review覆盖。
- 与既有status一致：complete分析使用met（即使发现问题）或已论证不适用时not_applicable；partial/not_started保持unknown或not_met。不能批量设met。review可缺省于早期事实草稿，但交付内部评估时必须逐维度补写，不能输出初始化占位。真正未开展的事项按具体原因如实列示，不强迫虚构判断。

先核对事实与已有风险分析，再归纳各维度当前结果并回写这些记录；程序只做一致性和引用校验，不自动生成法律判断。既有设计、风险及措施已有依据的部分先评估，未明确事实只限制对应子项。复评沿risk_ids/action_ids/fact_ids依赖重开，pending_review_ids未清理时显示“变更后待复评”，旧发现不充当本轮结论。严禁为修复展示而清空未决依赖或修改原试验产物。呈现样稿若底稿缺这些分析，须实际补做记录衔接，不能继续仅重排默认值。

**合法性维度的简洁覆盖。** 内部报告的EU-C02.analysis按report-basis.md逐目的呈现候选路径及条件分析，不能只有“未定”。另须明确呈现eu.md中的特殊类别、犯罪数据判断，以及场景触发时终端存取/后续处理的区分；短句写清“当前判断—事实范围及依据—剩余限制”，不只在列名或法源栏写Art9/10。来源记入fact_ids/source_refs，法律推断不回填成业务事实。不适用可给有依据的排除理由；未知写具体限制，不能假装已评估，也不必为每个子项新增风险。生成后核对这些判断确实出现在正文，而不只存在于筛查记录、脚注法源表或.audit.json中。这是语义核对，不用关键词出现、模板勾选或结构校验通过代替。

## 两种报告状态
待完善草稿：保持meta.stage=draft，不伪造事实冻结或review_ready。缺失事实答案栏留空，原生批注“待补充/确认—合规影响—建议”；未知选择保持未选。已确认尚未设计、不删除等如实填正文，已知缺陷不能藏进批注。受缺口影响结论写明未定，标注评估尚未完成及覆盖限制。
内容已完成供审阅：必要事实、分析和程序状态足以支撑意见，可得负面结论，未解决重要条件明确列出；不冒充DPO意见、控制者批准或监管咨询完成。没有真实记录的签批留空。

旧dpia.py render用于完整门槛下的法律工作稿；不要降低其门槛生成提前报告。提前草稿按本文件由文档能力制作，使用已知事实、留空及原生批注，不加载旧测试场景或预写法律答案。程序输出不是自动合格的交付物。

## 正式模板与语言
需要模板才读official-templates.md，核验国家、原件、版本、效力及目标语言；保留栏目、选择语义和签批区。默认用户语言，不无需求并行多语；工作译本注明非官方。未知字段不代填，系统/部门不充当法人，候选法律基础不勾成已成立。
报告包括处理说明、适用依据、必要性/比例性、个人风险与措施、参与程序及复评；重要法律引用精确条款和官方原文，事实来源在脚注或索引。内部工程ID不用来代替业务答案；产品版本、DPIA文件版本、测试轮次分开。
DOCX调用documents能力并逐页检查内容、选择、批注锚点及版面，中文macOS使用用户级codex-render-docx。无原件、批注或渲染能力须说明限制，不伪装完成。

正式报告（包括待完善草稿）按[report-release.md](report-release.md)保留底稿到成品的对应关系。逐风险的legal_refs必须进入对应风险正文或其就近脚注，不得只输出legal_analysis并在文末统一列资料。未知字段在实际回答位置留空并就近批注，集中问题表不能替代这些字段的批注。草稿允许未知，不允许静默遗漏评估问题。

## 修订
记录report_id、assessment_id、revision_id、事实基线版本、模板及法源版本；报告不是身份来源。新材料先做变化影响判断，保留旧稿，不将其批准当作新版批准。每轮不默认重做Word；按用户需要输出对应版本。
