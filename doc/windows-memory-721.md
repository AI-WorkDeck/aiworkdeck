# Windows 8GB 文档编辑内存排查（dev-board#721）

2026-09-20；用户报告版本约 0.45.0、8GB Windows、软件本身约占 35%、打开一份文档，未使用本地语音/OCR。本机验证平台是 macOS，未取得该用户进程清单或 Windows 内存样本。

## 已确认机制与改动

`librePool.js` 在进入工作台后预热一套完整 LOWA。首份文档接管它后，`onLibreSpareReady` 又调度一套空白实例，长期驻留。v0.45.0 标签与本轮起点均存在此逻辑。文件体积权重预算只按压缩文档大小计算，小文档可留下六套常规引擎及一套空白引擎，没有计算每套引擎的固定开销。

本次在物理内存 ≤8GiB 或旧壳未提供内存值时：

- 保留首套预热及现有接管路径；有真实文档后不再补空白引擎，启动计时期间打开文档也不会重复创建。
- 两个常规实例作为驻留目标，活动分屏优先，沿原 `flushSave` 链淘汰旧实例；保存失败或保存期间重新激活必须保留。
- 分屏关闭时不计已卸载的右侧实例，重开时重新核算；直接右开文档时释放无法接管的左侧空白实例。
- 全部文档关闭后恢复首套预热；隐藏合并实例仍独立按需创建和释放。
- 已知 >8GiB 的设备保留原策略。物理内存只从主进程传一份静态值，不增加轮询或遥测。

功能取舍：首份文档仍有预热，最近两份可热切换；新开的第二份文档不再有额外备用引擎可接管，超预算被卸载的旧文档回切需重新加载。此优化不能宣称所有打开操作完全无延迟差别。仍然需要编辑引擎支撑排版、修订、批注与 DOCX 导入导出；共用单引擎多文档是另一项架构工程，未在本次冒险替换。

## 实测与口径

使用 Electron 30、本机 0.44.1 安装版内置 LOWA 资产，分别运行安装版包装层、当前源码构建的包装层。独立 BrowserWindow 各运行一套真实引擎；不是整个产品 UI，也不含 Java/Python。实验脚本为 `desktop/scripts/measure-editor-memory.js`，使用合成文档，无用户文件或网络回传。

| 工作集加总（MiB） | 安装版包装层 | 当前包装层 |
| --- | ---: | ---: |
| 一套引擎就绪 | 1580.34 | 1582.61 |
| 两套引擎就绪 | 2841.88 | 1828.83 |
| 销毁备用实例后 | 1541.63 | 803.02 |
| 关闭全部引擎 | 未采到（原临时脚本随关窗退出） | 231.38 |

两轮销毁备用实例分别减少约 1300、1026MiB 工作集，但第二轮原实例的工作集也发生变化，可能受系统内存压缩等因素影响。这是移除额外引擎能回收大量资源的证据，不是 Windows 8GB 产品总占用降幅承诺。工作集包含共享页，macOS 压缩会影响读数；[Electron 内存指标说明](https://www.electronjs.org/docs/latest/api/structures/memory-info)。

当前包装层实验还验证：备用实例销毁后，存活实例插入合成标记、导出 5185 字节 DOCX、重开并找回同一标记，均成功。测试返回 `edit=true, reload=true, markerPresent=true`。

## 未采用的推测优化

- Java 启动未设置堆参数；随包 JRE21 在模拟 8GiB 上限时默认初始堆128MiB、最大堆2048MiB。最大堆不是实际占用。合成分配256MiB、保留32MiB、空闲145秒后，默认RSS381.9MiB，60秒周期G1组386.8MiB，再加Xms64m组387.4MiB，没有支持改参数的收益证据，因此保持不变。
- ASR/Kokoro重型模型首次请求才加载；可选Python服务仍取决于组件安装情况，不能仅因“没使用”断言不存在进程。
- 剪贴板图片重复读取、上传缓存阈值、字体缓冲与反复载入的临时文件是进一步排查线索，尚未确认是用户本次35%的来源，未混入修复。

## 复测

Windows上需记录同一版本、同一文档、相同等待时间的进程工作集及私有内存：项目空闲、单文档、第二/第三文档、关闭文档、关闭/重开分屏、退出应用。重点确认单文档不再留额外空白引擎，文档编辑/自动保存/导出仍正确，并记录首次及第二份打开耗时。
