# 原生文档与旧项目接续样板：2026-10-25

本轮在实验窗口接通了正文输入、审阅列表、真实 Git 版本和旧项目身份接续，并在正常观察负载下复测。**Word 冷开有明显收益，完整启动仍受原 Java 初始化约束；尚未满足「明显提速且其他体验不受影响」的默认实现合并条件。** 保留实验分支，不合并产品入口，不发版，不移除 Windows。

窗口仍使用 Electron，文档模型和绘制使用原生 LibreOfficeKit。Swift/SQLite 独立数据服务仍保留作对照；兼容旧项目的窗口由原 Java 负责 H2、文件和 Git 的全部实际写入。结果不能证明需要将整个界面改写为 Swift。

## 本轮接通的范围

- **正文输入**：透明输入控件跟随原生光标，鼠标和键盘映射到文档坐标；确认后的中文通过原生扩展输入提交，预编辑取消不写入正文。输入序号、文档代次和回执防止重复、迟到输入写进新模型。切换、恢复和退出先排空输入并保存；纯文本复制/剪切读取真实选区，空选区或剪贴板失败不会删除正文。
- **审阅侧栏**：读取真实作者、类型、完整修订文字与坐标；使用原生修订 ID 和当前快照定位、接受/拒绝。定位后核验 URL 绑定模型的实际光标范围；操作后重新核对目标层和其他已有条目。支持显示修订/最终稿两态，未知操作结果锁住当前通道。CAPI 和多步 UNO 操作在宿主中串行处理。
- **版本历史**：读取原后端的 Git 时间线、保存版本、恢复版本。恢复先关闭旧原生模型，再调用原后端恢复、重新下载并打开文件；新的操作回执到达后才报告成功。实测包含恢复后再次保存，防止旧模型把恢复结果覆盖掉。
- **旧项目接续**：兼容适配器检查后端构建、本地身份、存储根，保留项目/文件 ID、UID、路径和原 Git 库。SQLite 仅保存上次观察到的目录和未决操作保护；清除目录缓存不会清掉未知写入记录。

**旧项目接续不是 H2→SQLite 的完整迁移。** SQLite 目录不是事务快照；权威字节、保存和版本操作仍等待 Java。上传前 hash 校验不是服务器端 CAS，不能消除另一客户端同时写入的窗口。AI checkpoint、多窗口、文件监听和云端写入协议仍未迁移，不能给 Java 和 Swift 同时发放实际文件写权。

所有改动限定在 `desktop/prototypes/`；正常产品入口、前端、后端、打包和发布流程未变。第三方运行时、合成文档、数据库、截图和原始日志均留任务工件，不入库。

## 正常负载对照

固定完整产品基线 `8d9eddde694b521dc1abfde943a56ab2565f7698`，对应候选 JAR SHA-256 `66174b8659bb3fdb9e0dfa960e852db78588b3a6b2343ed418df98e3714733b5`。两侧使用同一份 60 段、600 修订 DOCX，SHA-256 `42d60dcc51b4329be843e38c96c305c1aea676eba678f01742fb46d28c84b50e`。

每次使用新进程、独立 HOME/H2/引擎配置，预置同一个合成旧项目。按 B1/A1/A2/B2/B3/A3 交替，任务内不并行构建或测试。窗口内容区 1280×900、DPR 2；运行时从 SSD 解压目录加载，OS 文件缓存未清空，Word 在项目出现后直接点击，没有为 WASM 留预热等待。实际宿主为 14 个逻辑 CPU；记录系统负载和 CPU 空闲，不将其宣称为完全受控压测。

| 项目工作台出现 | 6,516 ms | 6,055 ms | 减少约 7.1%，仍约 6 秒，不是显著改善 |

三轮窗口原始值：基线 6,522 / 6,516 / 6,315 ms，样板 6,055 / 6,051 / 6,060 ms。三轮正文首屏上界：基线 6,440 / 6,274 / 6,337 ms，样板 2,688 / 2,548 / 2,678 ms。采样开始时 CPU 空闲约 56%～72%；六轮全部正常退出，测试端口释放，已有服务未变。三轮原生版本恢复后再次保存均通过，最终文件另行回读验证 600 组原修订和三个文本投影。

Word 终点通过连续真实窗口截图判断纸张和文字，保留上一张未满足条件的时间，不使用空画布、模型就绪或备用引擎预热代替。两侧的字体/版式、功能范围与可编辑验收并不完全等价；实验窗口出现不能当作全产品完成启动，也没有证明复杂文档、更多项目均有相同比例收益。

前一组修复前的正常负载结果为窗口 6,192→5,977 ms、正文 6,235→2,711 ms。它保留在 `MEASUREMENTS.json`，本轮修复后结果另列，不混合选取。更早的高负载 19,998→1,090 ms 极简窗口，以及 15,424→4,405 ms Word 观察，仅保留历史工件，不能与正常使用或完整 Java 兼容窗口横比。

## 验证与失败记录

主任务实际执行：输入组件 **23/23** 测试、兼容层 **14/14** 测试通过。输入测试覆盖 composition 顺序、取消、重复回声、旧文档回执、坐标、冻结、保存、剪切失败；兼容测试采用 mock HTTP 与真实 SQLite，不能替代真实后端验收。另在独立 Java 21/H2/Git 上执行真实 API 测试，原 ID/UID、磁盘文件、版本恢复和清缓存后读取通过。前轮 Swift 数据服务 30 项测试为既有证据，本轮未改其实现。

原生探针实际覆盖 600 修订、原生 ID 接受/拒绝、过期快照、输入序号、关闭重开后的旧代次拒绝、中文导出回读；可选 UNO 回归包含同一插入/删除在 all/final/all 下重复定位，读取实际光标起止范围。相邻不同作者删除和叠加修订小夹具通过；拒绝上层删除后原插入层保留。表格 A1 内中文与 emoji 输入导出后只在目标单元格出现一次。

完整窗口 `ui-java-final-3` 已通过实际审阅、撤销、输入、版本创建、恢复、再次保存和正常退出。保存文件另由主任务读 ZIP/XML 核对：600 组原修订的类型、作者、日期、文字相同；第一版新增中文只出现一次，第二版与取消预编辑的文字均不存在；去掉唯一普通输入标记后 all/original/final 文本投影与原文件相同。XML 节点拆分不等于丢失修订。

本轮修复的实际问题包括：CAPI JSON 修订参数应使用 `uint32` 而非 UNO 的 `unsigned long`；显示枚举写 0 会被归一为 1，应读 `ShowChanges` 验证；删除修订选区的复制文本可以为空；重复获取临时 UNO 修订对象曾导致 SIGSEGV，改为单次获取并持有后回归通过。后者尚未证明上游生命周期根因，不能宣称所有原生崩溃问题已解决。失败试跑、崩溃摘要与成功复跑均保留，未计入有效性能统计。

真实 macOS 中文候选窗仍**未验收**。用户准许临时切换并还原已有输入源；应用范围的自动键盘操作没有显示输入源切换或候选窗，只观察到字母直接输入。没有成功切换证据，未安装输入法、未改设置；不宣称系统候选窗或输入源还原已验证。CDP composition 和原生中文提交通过只能说明程序输入链路。

## 合并门槛尚未通过

1. 接回原数据权威后，完整启动仍约 6 秒，未达到用户要求的明显改善。保留后端初始化依赖的缓存目录不是轻量数据层迁移完成。
2. 从正确的 **controller** 属性集查询，当前运行时仍缺 `AwdReviewGeometry`、`AwdReviewSidebarWidth`；完整三态审阅页边、气泡布局、关联修订分组处理尚未迁移。前轮仅查 model 的证据不充分，本轮已补正。
3. 系统输入法候选窗、富剪贴板、完整工具栏、多文档/分屏、复杂版式和完整 AI 命令/锚点/迟到结果协议仍未通过等价验收。
4. 旧项目完整迁移、跨客户端同时保存、watcher/云同步、AI checkpoint 恢复尚未完成。已测的普通 Git 版本恢复不能覆盖这些协议。

当前证据支持继续原生文档路线，也表明数据权威必须真正拆出启动关键路径；尚不支持将这个样板切为默认编辑器或以 Swift 重写来承诺整机启动速度。
