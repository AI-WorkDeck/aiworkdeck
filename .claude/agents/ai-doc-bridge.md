# AI↔文档编辑桥接 领域地图

职责边界：AI 侧发出编辑指令 → 编辑器执行 的整条链路。不含编辑器内核本身（那是 doc-editor 领域），不含对话编排（ai-chat 领域）。

## 段落号基数：doc_* 全族 0 基（已踩）

编辑器侧一律 0 基——`office_thread.js` 的 `get_paragraph` / `modify_paragraph` /
`select_paragraph` 都是从 `i = 0` 起数、`i === idx` 命中，`get_document_text` 返回的也是
`index: i`（0 起）。可 `doc_get_paragraph` 与 `doc_modify_paragraph` 的 `@P` 曾写
「段落索引，从 1 开始」，而同族的 `doc_get_document_text`、`doc_select_paragraph` 写的是 0 开始。

模型先用 `doc_get_document_text` 拿 0 基编号，再照「从 1 开始」的说明去调
`doc_modify_paragraph`，就整体差一段——**在修订模式下改错条款**，用户还很可能直接接受。

**新增任何段落定位参数，说明里必须写明 0 基**，并且缺参要在 Java 侧拦下：编辑器的
`Number(p.index) || 0` 会把 null／非数字静默当成第 0 段，「没给段落号」于是变成「改第一段」。
回归用例 `ParagraphIndexBaseTest`（反射扫 `@P`，写成 1 基即转红）。

**matchIndex 是唯一的例外：模型面 1 基、worker 0 基，在后端归一**（2026-09-02 顺带修掉）。`doc_replace_nth_match` / `doc_delete_match` 的描述、system prompt 第 7 节第 3 条、`ToolRegistry.LEGACY_DEFAULTS`（缺省 1）都对模型说「第 N 处，从 1 开始」，而 worker 的 `replace_nth_match` / `delete_match` 与它的其它整数定位一样从 `i = 0` 起数——原先后端原样透传，模型说第 1 处改的是第 2 处。归一落在 `DocumentEditTools` 下发前减 1，**不改 worker**：JAR/Web 插件经 `PluginHostImpl.DOC_ACTIONS` / `pluginDocActions.js` 直接按 worker 契约调这两个 action。回归 `MatchIndexBaseTest`（后端换算）+ lowa-e2e 组 11 末两步（worker 0 基钉住）。

同类：`doc_goto` 的描述曾宣告 `paragraph/bookmark/line` 三种定位，而 `office_thread.js` 的
`goto()` 只实现 `start/end`，其余一律返回 "goto type not supported yet"——
**描述里挂着做不到的能力 = 模型反复往死路上撞、白烧步数预算**。已收窄成只宣告 start/end，
并指向 `doc_select_paragraph` / `doc_select_anchor`。

**修订机制（redline）**
- `office_thread.js` 内：`minimalEdits()`（公共前后缀裁剪 + `myersEdits()` 字符级 Myers diff）与 `applyMinimalRedline()`（从右到左应用，只对差异段打修订）；`setRedlineAuthor`：`__agent` → 署名 "AI WorkDeck"，否则用户名。
- **颗粒度契约（dev-board#365，PR#188 的续篇）**：
  - **在哪层**：只在 worker（最靠近引擎的一层）做 diff。后端 `DocumentEditTools` 只透传 `findText/replaceText/newText`，不做任何拆分；前端执行器不碰文本。修订对象只有引擎能造，diff 离引擎越近，越不会被中间层的字符串处理（trim/换行归一）带歪。
  - **什么粒度**：**字符**（JS code unit），中文不分词、不按行/按段。`range.setString(newText)` 在 RecordChanges 下是「整段删 + 整段插」，所以每个替换类原语（`find_replace` 逐命中路径 / `replace_nth_match` / `modify_paragraph` / `replace_at_position` / `replace_selection`）都先 `minimalEdits(old, new)` 拿到 `[{start, delLen, insText}]`（旧串坐标、**降序**），再逐条 `goRight(start)` + `goRight(delLen, true)` + `setString(insText)`：每条片段落成一对「删 X 插 Y」真修订；纯插入走 `insertString`。从右到左应用是硬约束——左边先改会让右边片段的偏移全部失效。
  - **为什么是 Myers 不是 LCS DP**：PR#188 的 LCS DP 有 500x500 上限（`oMid.length * nMid.length > 250000` 直接整块替换），法律条款一段动辄六七百字，首尾各改一个字就整段删了重写——这就是 #365 用户看到的「整段删除后重写」。Myers 的代价是 O((N+M)·D)，只随差异步数 D 增长，段落再长、只改两个字也只产出两条片段；D 超过 `MINIMAL_EDITS_MAX_D`（2000）说明整段面目全非，退化成「掐掉公共前后缀后整块替换」——那本来就是重写。
  - **碎片化的折中**：两条片段之间只隔一个巧合相同字（中文里常捞到「的/、/方」）时并成一条（`甲方三→乙方五` 是一条，不是两条夹一个「方」）；隔两个字以上保持分开。不做更激进的合并——那会把整句吞掉，正是要修的病。
  - **`find_replace` 全部替换的分流**：默认 `replaceAll=true` 走引擎原生 `XReplaceable.replaceAll`（`nativeTrackedReplaceAll`，150 命中 0.2s），它只能把「掐掉公共前后缀的中段」整块替换。`replaceAllIsSingleBlock(findText, replaceText)`（= `minimalEdits` 结果 ≤ 1 条）为 false 时（一句里两处散点改动）**不走原生路径**，改逐命中 `applyMinimalRedline`（命中 > 50 分批 + 进度 + 可取消）；单块差异（甲方→买方、我爱你→我恨你、纯插入）仍走快路径，大文档批量替换的性能不受影响。
  - **回退到整块的情形（不是 bug）**：旧/新文本含段落符或代理对（`goRight` 与 `getString` 的计数口径不一致）、纯插入到空 range、全量替换（脚本只有一条且覆盖整段）。
  - **模型层**：`DocumentEditTools.REDLINE_GRANULARITY_NOTE` 挂在五个替换类工具描述**末尾**，system prompt 第 7 节第 5 条同款——「未改动的文字逐字照抄原文，不要顺手改标点/润色」。引擎再细的 diff 也救不了模型把整句重新措辞。
  - **回归**：`frontend/tests/lowa-unit/minimalEdits.test.mjs`（`npm run test:lowa-unit`，抠 worker 纯函数在 node 里跑：我爱你→我恨你一删一插、一句三处改动三组片段、> 500 字段落首尾各一字只两条片段、随机小改动脚本套回恒等）；真引擎形态 lowa-e2e 组 11（含 `find_replace replaceAll` 三处散点、长段落、同段第二轮改动）；后端 `RedlineGranularityContractTest`（描述末位约束 + prompt 双语）。

## 核心数据流（以 doc_find_replace 为例）

1. `DocumentEditTools.doc_find_replace` 校验参数 → `executeEditorCommand("find_replace", …)`。
2. 编排器在此前已因 `fileEffect="MODIFIED"` 对 activeFileId 建检查点（幂等，一轮一次）。
3. EditorBridgeService 生成 requestId、Future 入 pendingRequests，经 SSE client_action **双轨各发一份**（先 `tool=editor_command` 后 `tool=wps_command`），然后阻塞 30s。
4. 前端 useAgentStream → project-overview.vue `handleClientAction`（latch 去重）→ `handleEditorCommand` 附 `__agent:true` → executor。
5. executor 校验 EDITOR_ACTIONS → worker postMessage → office_thread.js 执行（RecordChanges=true → 逐处 applyMinimalRedline，失败回退 setString）。
6. 结果按 reqId 回流 → `POST /api/ai/agent/editor-result` → completeEditorAction 解锁 Future → 工具返回给模型。

## doc_* 原语速查（工具名 ≠ 下发 action 名）

全集见 DocumentEditTools.java。易混对照：`doc_find_text`→`find_text_locations`、`doc_select_anchor`→`set_selection`、`doc_replace_at_anchor`→`replace_at_position`、`doc_collapse_cursor`→`collapse_selection`、`doc_start_stream`→`doc_open_file_sync`+setStreamingMode。批注 `doc_add_comment`→`add_comment`。格式面：`doc_apply_standard_format`→`apply_house_style`、`doc_set_numbering`→`set_numbering`、`doc_format_table`→`format_table`、`doc_insert_table`→`insert_table`（rowsJson 后端解析成 rows 数组下发）、`doc_get_formatting`→`get_formatting`。

**Word 表格单元格级原语 `doc_table_*`**（issue #261；工具名去掉 `doc_` 前缀即 action 名）：`doc_table_read`→`table_read`（读成二维数组，改表前的眼睛）、`doc_table_set_cell`→`table_set_cell`（cell 形如 `B2`）、`doc_table_add_row`/`doc_table_delete_row`→`table_add_row`/`table_delete_row`、`doc_table_add_col`/`doc_table_delete_col`→`table_add_col`/`table_delete_col`。与整张表粒度的 `insert_table`/`format_table` 互补。worker 侧：定位与校验集中在 `resolveWriterTable`（tableName / tableIndex 0 开始 / 缺省用光标所在表；非 Writer 文档返回 `NOT_TEXT_DOC_MSG`），单元格坐标解析 `parseCellRef`/`parseColumnRef`，失败统一走 `tableFail()`——**同时写 `error` 与 `message` 两个字段**：前端 `handleEditorCommand` 只把 `result.error` 回传后端，只写 `message` 的话模型收到的是 `{"error": "null"}`（判得出失败但看不到原因）。`table_set_cell` 在 RecordChanges 开启且原格非空时走 `applyMinimalRedline`（与 replace_selection 同口径，只对差异字符落修订，返回 `via: 'minimalRedline'`），并把视图光标停在该格（后续原语可省 tableIndex）。增删行列用 `XTableRows/XTableColumns.insertByIndex/removeByIndex`，**删除侧按"行数变化 OR 修订条数变化"双口径判定生效**（修订模式下引擎可能记成删除修订而行数不变），返回 `removedRows/removedCols`、`redlineDelta`、`trackedAsRevision`。合并单元格本期不做；表里有合并/拆分格时 `table_read` 返回 `note` 提示那些网格位置取不到、单元格级修改会失败。真机回归见 lowa-e2e 组 20。

**电子表格（Calc / xlsx）sheet_\* 原语**：doc_\* 是 Writer 专属（`xModel.getText()` 在 Calc 文档上必然失败），xlsx 走 sheet_\* 全集（工具名=action 名，不做映射）——单元格面：`sheet_get_overview / sheet_read_range / sheet_write_cells / sheet_select_range / sheet_format_cells / sheet_set_borders / sheet_set_row_col`；结构面：`sheet_manage_sheets`（工作表增删改名移动）/ `sheet_edit_rows_cols`（插删行列）/ `sheet_merge_cells` / `sheet_sort_range`（XSortable，SortFields 是纯 Array of TableSortField 值结构体）/ `sheet_set_autofilter`（经命名 DatabaseRanges，set 语义而非 .uno: toggle）/ `sheet_freeze_panes`（XViewFreezable）/ `sheet_conditional_format`（命中外观落自建 CellStyle `__awd_cf_N`，每次调用替换区域现有规则）；`sheet_create_file` 是纯后端工具（POI 建最小空白 xlsx + 注册 + sendOpenFileAction，无 worker action）。worker 端 `resolveSheet` 统一守卫文档类型（非 Calc 返回明确错误）并把命中的工作表切为活动表。Calc 没有 redline，写入即生效——安全网是 doc_undo 与文档检查点（写类工具都打了 `fileEffect="MODIFIED"`）。地雷：`VertJustify` 声明 long、个别引擎按 short 校验（失败退 shortAny）；写入时数字样式字符串落数值但**前导 0 的编号保持文本**；数字格式经 `getNumberFormats().queryKey/addNew`（非法格式码会抛）；**setFormula 走 API 文法**——参数分隔符必须分号（逗号 Err:508）、跨表引用必须 `Sheet.A1`（`Sheet!A1` 报 #NAME?），worker 的 `normalizeFormula` 在字符串字面量外做 `,`→`;`、`!`→`.` 归一（Excel 数组字面量与 Calc 交集操作符 `!` 被牺牲，AI 公式里趋近于零）；引擎 LO 24.2 **无 XLOOKUP**（24.8 才有），出错公式经 `sheet_write_cells` 返回值 `formulaErrors` 报给 AI 自纠，读回侧 `readCellOut` 先查 `getError()`（否则错误格伪装成 0）。

## 演示文稿（Impress / pptx）slide_\* 原语（Phase 1+2+3：打开/读取/文本编辑 + 页与形状结构 + 格式与表格，已收官）

设计依据：`docs/superpowers/specs/2026-08-07-impress-bridge-design.md`（引擎具备性查实、原语全表 20 个、分期实施）。r4 引擎起 Impress 模块随 `--with-wasm-module=calc writer impress` 编入（r3 及以前只有 Writer+Calc，`probe_modules` 的 `simpress` 会报 `IllegalArgumentException`）。Phase 1+2+3 已在 r4 真机验证通过（lowa-e2e 组 21/22/23 全绿）。

与 `doc_*`（Writer）/`sheet_*`（Calc）三分，工具名 = action 名不做映射（沿用 `sheet_*` 口径）。**Phase 1**（打开/读取/文本编辑）：`slide_get_overview`（每页页码/名称/版式/母版/标题/形状数/是否有备注/是否含表格，打开演示文稿的第一步）、`slide_get_page`（单页明细：尺寸/版式/母版/备注 + 每个形状的名称/类型/位置尺寸(磅)/文字/**格式**(见下)，表格形状带行列数）、`slide_read_notes`/`slide_write_notes`（备注页读写）、`slide_goto`（视图切页 + 可选选中形状，拟人：操作要让用户看得见）、`slide_set_shape_text`（整体覆盖形状文字）、`slide_replace_text`（跨页/单页查找替换，覆盖文本框与表格单元格，缺省只替第一处、`all:true` 全部替换）。**Phase 2**（页与形状结构，spec §4.2 原语 8-15）：`slide_add_page`（position 1 起插到第 N 页之后/缺省末尾，title/body 走手工文本框而非 AutoLayout 占位符——见下方地雷）、`slide_delete_page`（拒绝删到 0 页）、`slide_move_page`（重排，`movePageTo` 统一实现）、`slide_set_layout`（AutoLayout 常量和/或母版名，谨慎使用——见下方地雷）、`slide_add_text_box`/`slide_add_shape`（矩形/椭圆/三角形走 CustomShape+CustomShapeGeometry/直线，位置尺寸磅值有默认值）、`slide_delete_shape`（按 shapeName 精确删）、`slide_set_shape_geometry`（移动/改尺寸，返回 before/after）。

**Phase 3**（格式与表格，spec §4.2 原语 16-20 + 任务方点名补的两项）：`slide_format_text`（字体/字号/粗斜体/下划线含 wave/删除线/颜色/段落对齐；不传 `anchorText` 格式化整个形状文字，传了则只格式化命中子串的第一处——真机验证过范围内/范围外字符互不影响）、`slide_format_shape`（填充色/边框色粗细/透明度，`noFill`/`noLine` 取消填充边框；**不在 spec 20 个原语表里，是任务方在实施指令里直接点名要补的一项**）、`slide_add_table`（`rowsJson` 给内容按其行列数建表写满，或按 `rows`/`cols` 建空表；新建 `TableShape` 默认行列数不定，统一按"目标行列数 - 当前行列数"的差值调 `insertByIndex`/`removeByIndex` 补齐）、`slide_table_read`/`slide_table_set_cell`（row/col **0 开始**——与 `doc_table_*` 的字母坐标不同、与插件 `office_ppt_table_*` 的 Office.js 整数坐标口径一致；不传 `shapeName` 时要求该页恰好一张表格形状，多张时报错要求指定，不悄悄挑一张）、`slide_table_set_style`（表头加粗/边框/列宽三项各自独立生效，r4 真机三项全部生效，见下方地雷段落）、`slide_set_hyperlink`（优先给选中范围设 `HyperLinkURL` 字符属性，与 Writer 的 `set_hyperlink_at_anchor` 同一实现口径；**r4 真机上这条路走不通，见下方地雷**，自动退化为形状级 `OnClick=ClickAction.DOCUMENT`+`Bookmark=url`——返回值 `via` 字段区分 `'HyperLinkURL'`/`'shape-click-action'` 两种情形；`slide_table_set_style` 与 `slide_format_shape` 均为**任务方直接点名**、不在原 20 个原语表里的补项）。`slide_get_page` 的非表格形状条目新增 `format` 字段（首字符代表值：fontName/fontSize/bold/italic/underline/strikethrough/color/alignment），读法与 `doc_get_formatting` 同口径，供 `slide_format_text` 调用方核实真实生效值而非只信返回的 `applied` 回声。

**真机地雷（r4 实测）**：oox 导入的 pptx 备注页占位符只上报 `com.sun.star.presentation.Shape`——具体子类型 service 名（NotesTextShape 等）在 supportsService/getSupportedServiceNames 里**不出现**，靠 service 判定备注框必失败；worker 的 `findNotesTextShape()` 三级回退（service 判定→占位符名 "Notes Placeholder"→排除已知非备注占位符后取最大可文本形状）是唯一可靠路径，别退回单一 service 检查。真机回归 lowa-e2e 组 21（fixtures/impress-smoke.pptx，27 步）。

**Phase 3 真机地雷（r4 实测，e2e 组 23 实锤，两个，均已在本分支修复/规避，非假设）**：
1. **表格形状分类判定失真**：用 `xModel.createInstance('com.sun.star.drawing.TableShape')` + `page.add()` 程序化新建的表格形状，经 `page.getByIndex()` 重新取到的引用上 `supportsService('com.sun.star.drawing.TableShape')` 报 **false**，但它的 `Model` 属性货真价实是一张能读写行列的 `XTable`（`slide_add_table` 内部用同一属性建表、调行列数都成功）——`shapeKind()` 原先纯靠 service 名判定，把这类表格分类成 `'other'`，连带 `slide_get_page`/`slide_get_overview` 的 `isTable`/`hasTable` 都失真，`resolveSlideTable` 按 `shapeKind !== 'table'` 拒绝合法表格。已修：新增 `isTableShape()` 鸭子类型判定（`getPropertyValue('Model')` 拿到后检查是否有 `getRows`/`getColumns` 方法），`shapeKind()` 的表格分支改成 `supportsService(...) || isTableShape(shape)`，service 名判定继续保留、鸭子类型判定作为补充路径，不影响真实 pptx 文件里原生表格走 service 判定命中的既有路径。这是 Impress 表格分类判定在这个引擎构建上的通用限制，不是 `slide_add_table` 独有的坑——任何"程序化建表后立刻用 `shapeKind()`/`resolveSlideTable` 定位"的路径都会踩到，改这块代码前先确认没有退回纯 service 名判定。
2. **字符级超链接在 Impress 上不存在**：`cur.setPropertyValue('HyperLinkURL', url)` 在 Writer 的 `com.sun.star.text.Text` 上是标准做法（`set_hyperlink_at_anchor` 已验证多年），但 Impress 的 `com.sun.star.drawing.Text`（形状文字）**不实现这个字符属性**，真机直接抛 `UnknownPropertyException`——与 spec 调研阶段"drawing.Text 尽量复刻 Writer 功能"的预期不符，字符级精度在这个引擎构建上做不到。`slide_set_hyperlink` 已按 spec 备选方案实现自动降级：形状级 `OnClick=ClickAction.DOCUMENT`+`Bookmark=url`（Impress UI「交互」面板同款机制，点击形状任意位置都会跳转），返回值 `via` 字段如实标注走的是哪条路径（`'HyperLinkURL'` 精确到字符 / `'shape-click-action'` 整个形状降级），`note` 字段在降级时说明代价。调用方/测试都不应假设字符级精度必然达成，要看 `via` 字段。
**表格边框/列宽的好消息**：`slide_table_set_style` 的三项（表头加粗、单元格边框、列宽）在 r4 上**全部真机验证生效**——Impress 表格单元格确实暴露 `TopBorder`/`BottomBorder`/`LeftBorder`/`RightBorder`（`BorderLine2` 结构体）与列的可写 `Width` 属性，比 spec 调研阶段"UNO API 面比 Word/Calc 窄很多、不确定能不能做"的悲观预期要好；工具仍保留"能做多少做多少"的 try/catch 隔离与 `applied:false` 诚实报告路径，以防其它引擎构建/版本上这两项确实不可用。

worker 端（`office_thread.js`）三个 resolver 集中文档类型与定位守卫（对标 `resolveSheet`/`resolveWriterTable`）：`isImpressDoc()`（`supportsService('com.sun.star.presentation.PresentationDocument')`）、`resolvePage(p)`（`slideNumber` 1 开始校验越界，命中后 `setCurrentPage`）、`resolveShape(page, p)`（按 `shapeName`/`matchText` 定位，未命名形状经 `ensureShapeNames` 补 `__awd_shape_N` 稳定名）。失败统一走 `slideFail()`，同时写 `error`/`message` 双字段（同 `tableFail` 口径）。非 Impress 文档报错文案对标 `NOT_SPREADSHEET_MSG`：「当前打开的不是演示文稿：slide_\* 原语仅对 pptx/ppt/odp 生效…」。位置/尺寸对外一律**磅**，worker 内换算（UNO 的 Position/Size 值结构体单位是 1/100 mm）。

**Phase 2 真机地雷（r4 实测，三个，均在 lowa-e2e 组 22 复现并已在本分支修复/规避，非假设）**：
1. **`XDrawPages.insertNewByIndex(nIndex)` 在文档已经历过一次插入后，同一文档上再插入（任意索引，边界/非边界皆复现）会连带清空某个"仅标题"版式（无内容占位符）既有页的标题占位符**——与新页塞了什么内容完全无关（裸调、不加任何内容也一样复现，`debug_impress_bare_append` 探针实锤），疑似引擎对 AutoLayout 占位符的重算逻辑本身有 bug，非 worker 调用方式所能避免。`slide_add_page` 用"插入前拍全篇标题快照、插入后逐页核对补回（手工建一个 `presentation.TitleTextShape` 塞回原文字）"自愈兜底，保证净效果不丢内容；标题/正文占位符也因此**不再经 `page.setPropertyValue('Layout', ...)` 生成**，改为手工 `createInstance('com.sun.star.presentation.TitleTextShape'/'OutlineTextShape')` 直接 `page.add()`（不碰 Layout 属性，`shapeKind()` 仍能识别为 'title'/'placeholder'，读取面代码不用改）。`layout` 参数仍可显式传入单独生效，但**多页文档上谨慎使用**（`slide_set_layout` 同款风险，工具描述已写明）。
2. **把一页"挪进真正的最后一页"这最后一步会卡住**：无论连续派发 `.uno:MovePageDown`（例如 4 页文档从 index0 连发 3 次只挪到 index2，到不了 index3）还是改派发 `.uno:MovePageLast`，都只挪一步就不动了；反方向没有这个毛病。`movePageTo()`（office_thread.js）统一实现挪页：目标不是"真正最后一页"时用逐步 Up/Down + 每步用 `Number` 属性核对（`movePageStepwise`）；目标就是最后一页时改用**交换法**——先把 page 挪到倒数第二（常规、非边界移动），再把此刻排在最后的那一页用 `MovePageUp` 往前挪一步，等价于把 page 换到了最后。副作用：交换法可能让"被交换的那一对既有页"之间相对顺序也跟着换一次——`slide_add_page`/`slide_move_page` 的返回值与调用方断言都不应假设"追加/移动一页时其余页顺序绝对不变"，只保证内容不丢、目标页确实落在目标位置。
3. **`ensureShapeNames` 按纯 loop index 拼 `__awd_shape_N` 会撞车**：标题占位符形状会在页面经历其它结构性操作（加形状/加文本框等）后被引擎悄悄重建（对象换了个新的、未命名），若重建后恰好落在某个"之前已经用掉这个数字"的下标上，两个不同形状会拿到同一个名字，按名定位（`resolveShape`）取到错的那个（e2e 组 22 实锤：矩形形状的名字后来指向了标题形状）。已修：先收集页面上已占用的名字集合，分配新名字时跳过已占用的，保证同一页内任何时刻名字唯一（不再是"按 index 直接拼"）。

诊断 action `get_doc_kind`（返回 `{kind: 'writer'|'calc'|'impress'|'unknown'}`）与 `load_document` 成功返回值里的 `kind` 字段共用同一判定（`docKindOf()`）：宿主（`LibreOfficeEditor.vue` 的 `docKind`/`showsReview`）据此隐藏「审阅」按钮与 `ReviewPanel`——Calc/Impress 都没有修订机制，此前只有 Word 隐藏，Calc 一直漏了，本次一并补上。

Impress **没有 redline**：`slide_write_notes`/`slide_set_shape_text`/`slide_replace_text` 都打了 `@ToolMeta(fileEffect = "MODIFIED")`，安全网是编排器在本轮首个 MODIFIED 工具前建的文档检查点 + `doc_undo`，工具描述里已对模型明说「PPT 没有修订机制，改动直接生效」。`retarget`（`load_document` 内）对 `RecordChanges`/`showDeletionsInMargin` 两步加了 `isWriterDoc()` 前置守卫——此前对 Calc/Impress 也无条件调用，靠 try/catch 兜住但会白抛异常打噪声日志。`stream_insert`（`doc_start_stream` 的落字端）加了 `isWriterDoc()` 守卫直接报错——`HOUSE` 排版语义（首行缩进/段后间距）在幻灯片上无意义。

宿主 tab 路由 `fileOpenTabs.js` 的 `wpsFormats` 加了 `pptx/ppt/pptm/potx/odp`：桌面 + 引擎可用时 pptx 走编辑器（`useLibreEditor`），web/h5 或引擎不可用仍走 `FilePreview.vue` 的 `pptx-preview` 分支（`libreOfficePreferred` 把关，`FilePreview.vue` 无需改动）。`ContextAssemblerService` 的 LOWA 分支按 `lowaDocKind()`（fileType/文件名后缀判定）三分：docx→doc_\*、xlsx→sheet_\*、pptx→slide_\*，末位提醒（`activeDocumentReminder`）同步三分。

**Phase 1 未做、明确延后的项**（spec §5.2/§6 已标注理由，不是遗漏）：LRU 保活权重（Impress 实例记双倍权重）——spec 原话「具体阈值在 Phase 1 用真实 pptx 测了内存再定」，没有真机内存数据前不写死阈值；预热备胎过继到 Impress 文档的稳定性——架构上不需要改（池按 key 存实例，与文档类型无关），但"同一 Qt 窗口从 Writer view 换成 Impress view 是否稳定"必须真机验证，若不稳定的退化方案（pptx 不吃备胎）也留给真机验证后再决定要不要写。`layoutNameOf()` 的 `AutoLayout` 数值→名称映射是最佳努力（只覆盖几个常被引用的值，未逐值核对 idl），不影响原语契约，命中不了就回退 `null`。

## 纯文本 text_* 原语（dev-board#37：后端直读直写，不走编辑器桥）

- **输入**：link 的 `anchorText`（报告里那句陈述）+ 每个 target 指向文件的可读文本。取文本走 `EvidenceTextExtractor`：文档委托 `DocumentTextService`（与 `extract_file_text` 同一条链路，PDF=PDFBox 3、其余=Tika），图片走既有 `OcrService`（`PlatformAiUserScope.call(userId, …)` 显式带身份——核查跑在超时保护的工作线程上，ThreadLocal 不会自己跟过去）。**取不到一律返回 null**，调用方判 `unverifiable`。
- **只核四类可机器校验的要素**（`EvidenceChecks`，不调 LLM、不做语义判定）：`uscc`（18 位正则 + GB 32100-2015 校验位）、`date`（陈述里 `YYYY年M月D日`/`YYYY-MM-DD`，底稿侧比对年月日/`-`//`.` 八种写法）、`amount`/`ratio`（数字归一，容忍千分位与 万/万元/亿/亿元 换算；**陈述侧裸数字不算要素**，「3 名股东」不是金额）、`party`（项目 PARTY 标签名 ∪ 别名）。归一化两副视图：`compact`（NFKC+删全部空白，给包含判断——OCR 会把代码拆成空格分组）与 `spaced`（空白折成单空格，给数字扫描——删空白会把跨行的两个数字粘成一个）。
- **别名口径**：`Tag.description` 里<b>带标签</b>（别名/简称/又名/曾用名/alias/aka）才解析成别名清单（显式声明下限 2 字），加上「全称去掉组织形式后缀」的一个派生简称（下限 4 字）。不带标签的自由说明<b>不</b>拆——拿一句话去底稿里瞎命中比没有更糟。
- **缺证据 ≠ 矛盾（红线，别破）**：底稿读不出文字 / 陈述里没有可核要素 / 要素在底稿里查不到 → `ok=null` + `unverifiable`，`relation` **原样不动**、`confidence` 置空。只有两种情形判 `contradicts`：陈述里的 USCC 自身校验位不符；陈述与底稿两边都有 USCC 且值不同。日期、金额、主体名<b>永远不</b>产生矛盾（没有语义配对时分不清「这份材料里没这个数」与「这份材料说的是另一个数」）。
- **写什么**：每个 target 写 `relation`（supports/partial/contradicts）、`confidence`（contradicts=0 / supports=100 / partial=命中比例 / unverifiable=null）、`verify_json = {checkedAt, verdict, checks:[{kind,expected,found,ok,note}], note?, priorRelation}`（整条覆盖、幂等可重跑；`priorRelation` 留着人工改过的旧值，面板要回溯时不至于查无对证）。**不写 link.status**。link 层面的 verdict = 各 target 里最坏的一个。
- **超时与取消**：单份底稿抽文本 45s 超时（`Future.get` + `cancel(true)`，失败也缓存成「取不到」，同一份坏文件一批里只卡一次）；批内底稿文本 LRU 缓存 16 份 × 20 万字符上限；批量墙钟预算 90s；取消照 `PluginJobService` 的 `AtomicBoolean` 轮询法，key = `projectId:userId`，取消要写权限。

**P3 网核 zip 接入（dev-board#100，`service/evidence/webverify/`，本仓内置、不联网）**：外部工具导出的 zip → 解包落进 `_网核/<主体>/<站点>-<日期>.<ext>` → 自动挂到报告里的网络核查段落。REST `POST /api/projects/{pid}/web-verify/import`（multipart `file` + `partyName` + 可选 `unifiedSocialCreditCode`/`sites`/`docFileId`，`controller/WebVerifyController.java`）+ AI 工具 `web_verify_import(partyName, fileId?, unifiedSocialCreditCode?, sites?, docFileId?)`（`service/ai/tools/WebVerifyTools.java`，zip 已在项目里时按 fileId 取，缺省时项目里恰好只有一个 zip 才自动用它）。
- **红线：只留接口，不做自动爬取**（维护者 2026-08-21 拍板，spec `2026-08-21-due-diligence-module-proposal.md` §6/§7 第 1 条）。`WebVerifyProvider` SPI 只有一个实现 `ManualWebVerifyProvider`（`providerId()="manual"`），它<b>不联网</b>；仓里不许出现登录、验证码、反爬、逐站抓取相关代码。`WebVerifySite` 枚举<b>不带任何 URL</b>（`WebVerifySiteTest` 钉着），它只是「这份材料来自哪个站」的标识。将来若接第三方合规数据服务，加一个 provider 实现即可，导入/挂链那侧不用改。
- SPI 形状：`List<WebVerifyResult> verify(WebVerifyRequest)`；请求 = `{partyName, unifiedSocialCreditCode?, sites[], archiveBytes}`（离线适配器必须有 `archiveBytes`，联网适配器会忽略它——同一条 SPI 兼容两种取数方式）；结果 = `{site, queriedAt, fileName, ext, bytes|sourcePath, rawText?, summary?, sourceUrl?}`。
- 包内解析两条路径，manifest 优先：`manifest.json`（任意位置，`items[].file` 可写全路径或纯文件名，字段 `site`/`capturedAt`/`sourceUrl`/`text`/`summary`）→ 文件名 `<站点>-<日期>.<ext>`。站点认 code/枚举名/中文名/别名，认不出是 `OTHER`；时间认 ISO-8601 与 `yyyy-MM-dd`/`yyyyMMdd`，认不出退回 zip 条目 mtime 再退回导入时刻（三级都是真实时间，不编）。manifest 自身解析失败只退回文件名解析并 WARN，不让整包进不来；但 manifest 里写穿越路径照样拒收，**不能从 manifest 绕过 zip slip**。
- 护栏（全部报错，绝不静默截断）：`ManualWebVerifyProvider.Limits` 默认 500 条目 / 512 MB 解压总量 / 64 MB 单条目 / 256 MB 整包；上限做成构造器入参只为让单测用几十字节的包验到超限分支。单条目大小**声明值与实读字节都过闸**——包里写的 size 会撒谎，只信实读（`rejectsOversizedEntryEvenWhenDeclaredSizeLies` 钉着）。路径含 `..`、以 `/` 开头或盘符式绝对路径（`C:\…`，网核包多来自 Windows 工具）一律拒整包。
- **挂链规则（宁可不挂，也不瞎挂）**：候选段落 = 报告里「已有 `method=web_check` 的 target」**且**「锚点文字/`sectionPath`/`sectionTitle` 里出现该主体名」的 EvidenceLink，两条缺一不可；候选里若有段落提到该站点（中文名或别名）则只挂这些，否则挂全部候选；一个候选都没有 → 只落盘，该件进返回值 `unlinked[]` 并带原因。写库只经 `EvidenceLinkService.addTargets`（证据关联的单一出口，不绕开它直接动两张表），新 target 固定 `relation=supports` + `method=web_check` + web 型 locator `{"type":"web","url","capturedAt"}`，`note` 取 manifest 的 summary。单条挂链抛错只让那一件进 `unlinked`，不回滚整批落盘。
- 落盘用 `ConflictPolicy.RENAME`（同站点同日重复导入得「(1)」副本）——**与 `_交付件/` 的「同名就地覆盖」相反**：网核件是证据，覆盖等于毁证；交付件是可随时重算的派生物。`ProjectFile.metaJson` 记 `{sourceUrl, capturedAt, provider, site}`（spec §1.2 的三件套 + 站点）。
- `docFileId` 缺省时按 `findDistinctDocFileIdsByProjectId` 唯一候选自动定位；0 份或多份**不报错也不猜**，落盘照常、`unlinked[]` 里说明原因（与 `dd_export` 直接报错的口径不同：那边不定位就没法导出，这边落盘本身已经有价值）。`sites` 里写了不认识的 code 则直接报错并列出可用取值——不能退成 `OTHER`，那会把用户的筛选悄悄变成全收。
- 测试：`WebVerifySiteTest`（识别口径 + 枚举不带 URL）、`ManualWebVerifyProviderTest`（zip slip 三形态、四类超限、manifest/文件名两条解析、站点筛选、系统噪音）、`WebVerifyImportServiceTest`（落盘路径与 metaJson、只挂 web_check 段落、站点收窄、未挂链清单、挂链失败不回滚、鉴权与跨项目、主体名清洗）、`WebVerifyControllerTest`（4010 信封与 multipart 透传）、`WebVerifyToolsTest`（fileId 定位、跨项目拒绝、摘要含未挂链清单、工具描述与站点枚举同源）。

- **能力过滤靠工具名前缀**（doc_/sheet_/office_，office 内再按 office_excel_/office_ppt_ 细分宿主）：新增 LOWA 专属或插件专属工具必须沿用对应前缀，否则会漏到不该见它的会话里（Excel 面起名不带 office_excel_ 前缀 = 漏进 Word 会话的死路径）；ToolRegistry 构造器加了 ClientCapabilityService，改它要同步 RecordingToolRegistry（EvalHarness）与各测试构造点。

- **PPT 表格门槛按 1.8 收紧、不是矩阵最初猜的 1.9**：`Table.rowCount/columnCount/values/getCellOrNullObject` 与 `ShapeCollection.addTable`/`Shape.getTable` 全部落在 PowerPointApi 1.8；`TableRowCollection`/`TableColumnCollection`（行列集合对象本身）才是 1.9，本批次未用到。别把工具门槛错设成 1.9，会让本可用的 1.8 宿主被拒之门外。
