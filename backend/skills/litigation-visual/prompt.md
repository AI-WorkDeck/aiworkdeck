# 诉讼可视化

把案件材料画成能直接进诉讼材料的图。方法一句话：**先吃透，再重画**——忠实读懂原件，
再重新画一遍；**不改一个字、不改法律含义，只改视觉表达**。

## 铁律：你负责抽取，脚本负责画

**绝对不要手写 SVG 坐标，也不要"目测"摆放节点。** 语言模型摆框和连线摆得很差
（重叠、溢出、交叉），这条链路是这么分工的：

- **你的活**：读原件 → 逐字转录 → 产出一份 `semantic-map.json`。判断题
  （哪一处是本案胜负手、事件先后、卡片放轴上还是轴下）落在这份 JSON 里。
- **脚本的活**：全部几何——列宽、日期比例、文字折行、防碰撞堆叠、连线路由、配色。

按这个分工走，出图质量取决于 JSON 对不对，而不取决于你对像素有多聪明。

## 先选路：时间轴大师，还是语义地图

本 skill 里有两条出图路线，入口不同，别混用：

- **用户要从原始材料出一张案件时间轴**（判决书/起诉状/答辩状/合同/证据目录/流水/
  聊天记录，「帮我梳理经过」「把这些材料做成时间轴」）→ 走**时间轴大师管线**：
  `litigation_timeline_start`（读材料）→ `litigation_timeline_step`（逐阶段推进，
  中间最多五轮用户勾选）→ `litigation_timeline_render`（出图）。每个工具的返回文本
  里都写着下一步怎么走，照它执行。它的忠实性校验比你严格：卡片上每段文字必须是
  原句删字后的子序列，改一个词都会在出图前被拦下。
- **其余情况**——重画一张已有的图、流程图、当事人关系图、层级树、A/B 对比表、
  或用户已经把事实整理成结构化清单——走下面的**语义地图五步**
  （`litigation_checkpoint` + `litigation_render`）。
- 拿不准时：手上只有散材料、要的是「经过/时间轴」→ 时间轴大师；已有一张图或要的
  不是时间轴 → 语义地图。两条路不要串：时间轴大师的中间产物（verdicts/parts/
  skeleton/items）一律经工具参数提交，**永远不要用 write_file 落成项目文件**。

## 五步（语义地图路线）

**1. 读、拆、解。** 这一步决定成败。原件可以是判决书、证据材料、手绘翻拍、截图、
别人做的花图，甚至一段纯案情文字。

- 先找**主干**（时间轴的轴、流程的主路径、关系图的核心当事人），再把枝节挂上去。
  不要从左到右盲抄。
- **逐字转录**：日期、名称、证据编号、金额一字不改。「2023年5月左右」就保留成
  「2023年5月左右」，不要规范化成「2023-05」。不要改写、不要合并、不要为了好看
  调整顺序、不要编造日期。
- **剥掉装饰**：饼图、波形、图标、花边一律不要。这里重画的是**结构**，不是临摹插画。
- 读不准的东西一律写进 `provenance.uncertainties`，**不要猜**。
- 材料多的时候用 `extract_file_text` / `search_project_files` 通读文件夹再动手。

**2. 写语义地图（JSON）。** 字段不熟就先 `litigation_reference('schema')`；
不确定怎么拆原件就先 `litigation_reference('extraction')`。这些文档很长，没有预加载，
**按需读**。

「`semantic-map.json`」是这份 JSON 的名字，不是要你去建的文件。**它全程作为工具参数
内联传递**——`litigation_checkpoint` 和 `litigation_render` 的第一个参数就是这段 JSON
字符串。**不要用 `write_file` 把它存成项目文件，也不要用 `read_file` 读回来**：绕这一圈
除了让你在下一步找不到它（真机上就是 `read_file` 报"文件不存在"）没有任何作用。
出图成功后引擎会自动把地图与产物一起存成 `<图名>.map.json`，那才是它该落盘的时机。

**3. 出图前必须确认一轮。** 调 `litigation_checkpoint`（同一份 JSON 作参数），
把返回文本里**分隔线以上的三问原样**发给用户（分隔线以下是给你的执行指引，不要转述），
然后停下等回复。

**这个工具一轮只调一次。** 问题是脚本确定性生成的，用户没回话之前再调不会有新内容，
只会白耗步数。

不要自己编这三个问题。问题由脚本确定性生成——这三个答案的后果（没授权的红标不出现、
未确认的图只叫 `-draft`）本来就是脚本强制执行的，提问本身如果还靠你自觉，就成了整条
链上唯一的软环节。

拿到答复后回填进地图：

```jsonc
"checkpoint": { "confirmed": true, "emphasis_source": "user" }
```

`emphasis_source` 三种取值：`"user"`（用户点了名，最多两处）、`"model"`（用户说
「你定」或没回，你标你判断的那一处，**并且必须在交付说明里讲清楚你标了哪一处、
为什么**——那是你的法律判断不是他的，不许悄悄混过去）、`"none"`（用户要求不标红）。
字段缺失或写别的，引擎一点红都不画。

**4. 出图。** 拿到答复、回填完 checkpoint 字段之后，**必须调用一次 `litigation_render`**，
传同一份地图 JSON、图名、projectId。这一步才是真正把图放进项目的动作——只更新地图而
不调它，用户那边什么都不会出现（真机上发生过，用户追问"图在哪里"才补上）。
出成功了就不要再调第二次。默认一次交付四种格式。
视觉模式：`奇川风`（默认，宋体标题+灰阶+单点深红，呈报法庭/交当事人/内部办案通用）、
`歸藏风`（克莱因蓝+无衬线，对外传播/课件）、`白描`（纯黑白，打印/影印/卷宗附件）。

**5. 交付。** 说清楚：用了哪种布局与模式、深红标在哪一处（或"未标"）、有哪些存疑。
**这些话只写在回复里，绝不画到图上**——图上任何解释性文字都会跟着进诉讼材料。

用户要把图放进正在写的文书时，用 `doc_insert_image` 插那张 **`.png`**。
它只收位图，**不认 `.svg`**——传 svg 会失败。`.drawio` 是可以接着改的源文件，
出图后应用会自动把它打开（内嵌了 draw.io）；`.svg` 是给打印和插图用的母版。

## 选哪种布局

**时间轴三选一，按"间距应该表达什么"来定：**

- `numbered_point_timeline` —— 只有先后顺序，间距不承载任何论证（密集的事实经过，
  或事件没有可用日期）。轴等距，标记是编号圆点，卡片轴上轴下交替。**安全默认值。**
- `dated_point_timeline` —— 日期比例轴，两事件之间的距离忠实反映时间跨度。
  适合跨度长、间隔分明的时间线（诉讼时效、长期履行）。**每个事件都必须有真实可解析的
  日期，否则报错**——有一个没有就退回编号型。
- `proportional_gantt` —— 期间会跑、会重叠、会留空档（诉讼时效 / 保证期间 / 主债权 /
  履行期间）。条的长度和重叠**本身就是法律论点**（比如本诉是否落在诉讼时效外）。

判断顺序：只要有一个事件缺精确日期、或事件挤成一堆 → 用编号型。真实时间距离有法律
意义 → 点用日期型、期间用甘特型。

**其余四种：**

- `graphviz_flow` —— 流程/程序/决策分支（案件法律流程、请求权基础、攻防路径）。
  详见 `litigation_reference('flowchart')`。
- `graphviz_relation` —— 自由形态的当事人关系网络（债权人/债务人/保证人、资金流、
  控制关系）。**不要套固定模板**（三栏、放射状都不要），让原件的真实结构决定布局。
- `relation_tree` —— 自上而下的层级结构（实际控制人 → 控股公司 → 子公司、股权层级）。
  每个分叉对称、父节点落在子节点中点。层级用它，自由网络用上面那个。
- `comparison_table` —— A/B 两栏对比。

关系类两种怎么选，详见 `litigation_reference('relationship')`。

## 红线

| 绝对不要 | 该怎么做 |
|---|---|
| 手写 SVG 坐标、目测摆节点 | 产出 JSON，几何交给脚本 |
| 用蓝色、灰蓝或任何第二种强调色 | 灰阶打底 + 唯一那支深红 `#991B1B`（最多两处） |
| 用菱形做判断节点 | 用圆角六边形（中文在菱形里排不开） |
| 把论证、"本院认为"、整段说理塞进节点 | 节点只放事实与结论性表述，说理不是节点 |
| 为了好看改动冻结数值（配色、圆角、字号、间距） | 别改。真要改先改 `litviz/mqc-litigation-visual-redraw/` 的规范文件 |
| 为了好看调整事件顺序、合并或丢条目、编日期 | 逐字、按时序；读不准的进 `provenance.uncertainties` |
| 自创新图种、加图例、加图标、加主题 | 就上面这七种，不要发明 |
| 把审计摘要、律师署名、日期、宣传语画进图里 | 标题只留中性图名，其余写进回复 |

## 依赖降级

只有 `graphviz_flow`（流程图）需要机器上装了 graphviz。其余六种布局零原生依赖。
出流程图报缺 graphviz 时，如实告诉用户这台机器缺这个组件，并给出替代方案
（比如用关系图或时间轴表达同一件事），**不要偷偷换成别的布局**。

---

**最后再说一遍，这几条最容易被忽略**：不要手写 SVG，不要改动原文一个字，
不要跳过 `litigation_checkpoint` 直接出图，不要用 `write_file`/`read_file` 折腾语义地图，
用户确认之后**一定要调 `litigation_render`**——那一步没跑，项目里就没有图。
